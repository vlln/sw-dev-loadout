# 失败的设计

先回答三个问题：失败是什么、谁拥有处理、失败之后什么仍然安全。答不出第三个，就不要捕获。

## 类型化与结构化

预期失败要有声明的类型、稳定的判别标识、以及处理所需的细节。沿用包或项目已有的错误约定；保留原始原因；把机器身份与展示文本分开——**绝不用解析消息文本的方式决定处理路径**。

意外的缺陷（不变量被破坏、`assertNever` 走到）可以是普通错误，不需要为它们编造类型。但包含处理（containment）永远不能把缺陷变成成功：把未知失败包装成默认值返回，是比崩溃更贵的缺陷。

## 捕获、恢复还是停止

**捕获限制的是传播，不是变更。** 到捕获点为止，世界已经被改过了。只有受影响状态的所有者才能确立"可以安全继续"；其他人只能选择停止依赖工作、丢弃无效状态或实例、或升级。

- 能继续的前提是：后续工作所需的前置条件在恢复之后仍然成立，并且这一点有依据。
- 否则停止依赖工作，或丢弃无效状态，或升级。不要"记一条日志然后继续"——日志不是恢复。
- 清空一个可能已部分写入的结构，和恢复它，是两种不同的决定，选一个并说明。

每处失败都要在拥有它的 API 的文档里写清：哪些不变量仍然有效、效果是都没有、部分有、已提交还是未知、以及谁负责清理。

## 重试、预算与生命周期

重试需要三件事同时成立：操作可以安全重复、有取消路径、有明确的所有者。缺一条就不要重试。

- 有限操作要有预算：次数、总时长、退避上限。没有预算的重试是把一次失败换成一次资源耗尽。
- 持续监督型的工作需要生命周期所有权：谁启动、谁终止、终止时等什么信号、失败如何被观察到。
- 可取消的等待要真的响应取消，并在取消后回到一致状态。

## 状态保证

在拥有失败语义的 API 上，用一个明确的保证级别描述每次失败之后的状况：

| 保证 | 含义 |
|---|---|
| 无效果 | 失败后外部可观察状态与调用前相同 |
| 部分效果 | 可枚举的部分已生效，其余未生效且可识别 |
| 已提交 | 失败在提交之后发生，效果保留，补偿才是回退手段 |
| 未知 | 无法判定；调用者必须按最坏情况处理 |

写"未知"不是偷懒，是准确。声称"原子回滚"必须有机制支撑；没有机制就写未知，并给出探测或对账的办法。

后台任务、队列消费者、定时任务与请求路径承担同样的义务，不因"没人等结果"而降级。

## 可见的报告

每一个最终报告要包含三样：可读的摘要、受影响的操作、安全的下一步。

未受信状态与未知结果必须可见——通过界面，或通过默认开启且可访问的日志——报告影响、不确定性、系统处置与安全下一步。持续存在的无效状态需要持续可见，而不是启动时警告一次。

- 不得声称成功、已回滚或可安全重试，除非有对应的保证。
- 不泄露敏感内部细节到面向用户的文本；诊断细节走日志或诊断通道。
- 报告本身失败时要有独立的回退：报告不是唯一的失败通道。
- 走接收方应用的本地化机制；没有机制时沿用既有输出语言。

## 验证

验证的是结果状态与用户可见的结果，不是"异常被捕获了"。

- 断言失败之后的外部可观察状态，而不是断言 catch 块被执行。
- 对"未知"路径，断言系统进入了可识别的待对账状态，并且用户能看到它。
- 负控：故意注入一个预期失败，确认报告出现、状态符合声明的保证级别、且没有把失败吞成成功。

## 反模式

- 捕获后继续，且没有任何人证明后续前置条件成立。
- 把未知结果当成功返回，或把默认值当恢复。
- 用日志替代恢复。
- 无预算的重试，或无所有者的后台重试。
- 靠匹配错误消息决定分支。
- 面向用户的报告只有内部堆栈或错误码，没有下一步。
- 声称"已回滚"但没有补偿机制。
