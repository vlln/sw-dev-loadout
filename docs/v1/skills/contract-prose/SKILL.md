# 散文即契约

判据只有一条：**它承载的是契约还是转录。** 长度本身从不是缺陷。

契约是调用者、被调用者、实现者、生产者或消费者所依赖的义务、不变量、前置条件、后置条件或兼容承诺。

## 保留什么

- **行为**：它做什么，在什么前提下。
- **时序与模态**：同步还是异步、什么时候生效、能否重入、调用顺序要求。
- **异常与失败**：会抛什么、在什么条件下失败、失败后处于什么状态。
- **后果**：调用它会改变什么，谁会观察到。
- **所有权**：谁负责创建、谁负责释放、谁是权威来源。
- **安全使用条件**：并发约束、资源上限、不可重复调用之类。
- **非显然的定位**：为什么这里必须是这样——一句话加指向拥有理由的那处的链接。

## 删除什么

- 实现过程叙述（"首先我们……然后……"）。
- 显然分支的证明。
- 测试走查：逐行解释测试在干什么。
- 评审历史与来回讨论。
- 被否决的局部方案——那属于决策记录。
- 代码复述（`// 把 count 加一`）。
- 变更故事与版本印花："以前""现在""不再""曾经""被重命名""这次改动"。

理由只写在拥有它的那个位置（接口定义处、共享辅助函数处），不要在并列的每个实现旁边各抄一遍。

## 完整命题：删之前先数清楚

编辑之前先列出这段里的每一个命题，逐项确认保留：

- 行为者与动作；
- 条件、时序与顺序；
- 模态（必须、可以、绝不）；
- 否定保证与例外；
- 所有权、副作用、失败模式与后果。

只有在每条事实从句都存活、且结果更清楚时，才删形容词、重复与叙述。**字数变少本身不是进步**，把义务删成背书是最常见的过度修剪。

## 只写当前态

普通文档描述当前存在的代码。直接命名活着的机制，不叙述它经历了什么。

变更故事的家是：提交信息、PR 描述、决策记录、事故复盘。这些载体各自拥有历史；长期散文不承载它。少数刻意保留历史证据的记录（格式检查点、发布对比、已冻结的决策）属于它们自己的契约，不因此把历史叙述扩散到别处。

## 按位置覆盖

同一份标准，不同位置的义务不同。这是"该写什么"的清单，不是单向缩短的许可——当代码、类型与结构没有传达下列契约时，要补写。

| 位置 | 必须写到 |
|---|---|
| 公开 API 注释 | 调用者可见的返回区分、抛出与拒绝、副作用、所有权、时序、取消、持久性 |
| 内部注释 | 非局部结构的定向、不变量、竞态顺序、所有权、安全边界、出乎意料的失败行为 |
| 模块注释 | 模块的角色、依赖、职责、非显然的架构选择（并链接到拥有理由处） |
| 测试 | 只有非显然的测试设计：为什么需要这个 fixture、断言、平台适配、真实入口或间接观察 |
| 操作手册 | 前置条件、必需动作、真实入口、可观察的验证、简洁的告警 |
| README | 消费者契约：配置、语义、失败、限制、扩展点、对外可见的效果 |
| 决策记录 | 独有的理由、机制、备选、后果、已实现的验证证据、已命名的覆盖缺口 |
| 事故复盘 | 事故序列、证据、因果链、影响、预防 |
| 提示词与界面文案 | 措辞即行为：文本、无障碍名称、提示、占位符与格式模板一起看 |
| 诊断信息 | 失败的主体或路径、违反的规则、非显然的修正方式 |

空异常捕获必须写明它吞掉了什么、为什么不会有别的东西到达这里，且被包的语句只有一条。每个残留的类型逃逸要写明为什么不能用更窄的类型。待办按紧急度分级，选对级别，让扫代码的人一眼分清发布阻塞项与"哪天再说"。

## 泄漏：读起来像思考过程

一个测试：**一个站在当前版本、无法访问任何会话记录、PR 线程或未提交草稿的读者，能否解析每一个引用并验证每一条断言？** 不能，就把仍然成立的事实改写成从现在这个版本可读的形态，删掉其余。

八类常见泄漏：

1. 已失效的设计会话引用：`(decision 7)`、`(audit C2)`、`design §4.7`、`T4`、`P-I` 之类的阶段标签。有已提交的归属就按名字与路径引用，否则删掉引用并把事实改写成独立成立。
2. 栈与 PR 视角："这个栈里后面的 PR"、"本 PR 增加"。改成已发布的机制或扩展点。
3. 变更叙述与版本印花："used to"、"不再"、"旧的 X"、"v1"、"这一版"。
4. 评审编排："评审中否决了"、"评审者确认"、"这份笔记的第 5 稿"。
5. 对评审者的辩解："这个转换是安全的——只是……"。改成让它安全的不变量，或删掉。
6. 复述与推导转录：控制流叙述、测试走查、显然分支的证明。
7. 对冲与规划残留："目前大概可以"、"应该够了"、没有标记的延期。改成实际的边界或一个待办标记。
8. 撰写语言残留：正文语言里混进的未翻译片段。

**不是泄漏的**（这些是要求的散文，删了反而错）：issue 引用与带名字的待办、抑制理由与覆盖率豁免理由、空捕获说明、"没有 X 就会 Y"这类反事实回归钉、实测边界（"实测：512 层约 0.15 秒"）、运行时的新旧连接状态、外部标准与已提交文档的章节号、项目口吻的"我们"、决策记录里的备选段、事故复盘与本记录内的变更故事。

## 强调与语气

- 只给真正改变行为的那个从句留强调。加粗、全大写、"至关重要"到处出现等于没有重点。
- 一段讲一件事。一段里塞进好几条规则加括注补充时，拆开或把细节降级到它的家。
- 判据用"必须、不得、应当"，不用"注意""确保""尽量不要"。
- 读者是专业程序员：简洁直白优于比喻。不要滥用少数抽象名词——一个词到处用就失去区分度。
- 跨引用一律用可机械校验的相对路径链接，不用裸文件名、编号或纯散文描述。链接检查通常只校验文件存在，不校验锚点，锚点要自己核。

## 审计一份文档

按最便宜的探针先跑，再读语义：

1. 同一条规则有两个以上的家：搜一个特征短语，留一个家，其余改成链接。
2. 手抄的清单与枚举：测试列表、模块列表、门禁列表、API 列表——源码或生成器是权威时，手抄的一定漂移。
3. 状态标注与规划语气出现在已成事实的文档里："已实现！""未来会……""待迁移"。
4. 理由抄在并列成员旁边，而不是在拥有它的那一处写一遍。
5. 段落墙与强调通胀。
6. 空壳章节：标题存在但内容是"暂无""待补充"。要么写，要么删掉标题。

机械门禁查风格、结构与关键词，查不出"散文描述与实现语义不符"。绿门禁不等于文档可信：能机械对照的（状态名、行序、接口、字段值）建漂移门禁；不能机械对照的行为与触发描述，写明由谁在哪个环节核对，并要求产出结论、依据与证据路径。

## 动手顺序

1. 确认范围、模式与当前基线。没给范围就问清楚，不要自己扩大成全仓审计。
2. 先读拥有这段文字的代码或文档，再判断它该写什么。
3. 把待改的段落逐条分类：保留、补充、修剪、恢复、重构、延后。
4. 先改拥有者，再改派生物（生成的目录、快照、译文）。
5. 改完重读完整 diff，先看正确性，再看是否更短。
