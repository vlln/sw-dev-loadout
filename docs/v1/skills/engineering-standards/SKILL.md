# 可执行的工程标准

核心断言：**约定除非有程序会拒绝违规，否则等于不存在。** 只存在于对话历史或人类记忆里的约定，按不存在处理——假设代码的维护者会被随时终止，下次只能靠文件系统恢复上下文。

本文管一件事：一个改动凭什么有资格落地。项目处在哪个阶段、下一步做什么，属于另一层判断。

## 法则 1 · 常驻规则分层，一个事实一个家

每个会话都必须进入上下文的规则，集中在一个有字数上限的常驻文件里（通常是根 `AGENTS.md`）：每条 1–3 行、自包含、只链接不复述其详细归属。其余内容散到各自的唯一归属层。

常驻文件是立正命令表，不是手册。它放：项目定位一句话、目录布局、常用命令、必须常驻的约定、编辑本文件的规则。它不放：故事、完整示例、情境化流程、任何从被链接处复述来的内容。

| 层 | 它的工作 | 不属于它 |
|---|---|---|
| 根常驻文件 | 每个会话都需要的规则，每条 1–3 行并链接其家 | 故事、示例、情境流程、复述 |
| 子树常驻文件 | 该子树特有的命令 | 根文件已承载的全仓库规则 |
| 架构地图 | 模块、主流程、扩展点；改核心代码前必读 | 类型形状、单模块细节、决策理由 |
| 类型与接口目录 | 骨干词汇的字面形状与语义 | 行为叙述 |
| 决策记录 | 决策与理由，受自己的生命周期契约管辖 | 迁移计划、已完成的验收清单 |
| 事故复盘 | 事故故事；唯一允许战斗故事叙事的层 | 通用编码风格 |
| 危险模式文档 | 按危险领域分类的"缺陷类"规则，每条来自真实发生过或差点发生的缺陷 | 单次事故经过 |
| 菜谱 | "怎么新增一个 X"的编号步骤与结尾验证命令 | 设计理由 |
| 模块 README | 该模块的配置、语义、已知限制、扩展点 | 复述 API 注释、别的模块的事 |
| 生成目录 | 从源码再生成的穷尽枚举，由新鲜度门禁守护 | 任何手改 |

判定归属的顺序：先定位这个事实在树上被谁拥有 → 定它的细节深度（描述自己的主题可以详尽；描述直接子节点只写职责与高层行为；更深细节链接到拥有它的后代）→ 定它是教程还是参考。文档类型不扩大它的范围。

规则的写法决定它会不会被遵守：

```
差：注意保持代码风格一致，遵循现有约定。
好：跨包引用用包名，包内相对引用带扩展名；理由与例外见 <链接>。

差：重要改动要写文档。
好：每个非平凡改动必须在同一个 PR 内新增或更新至少一条决策记录；豁免范围见 <链接>。
```

规律：可判定（能对着 diff 回答是否违规）、有边界（说明例外或指向例外）、命名活着的机制（说"是"，不说"应该"）。

字数上限是强制机制而非建议，由门禁校验超限与文件缺失两个方向。红了以后依次：搬迁属于别层的内容（必要时留一行链接）→ 压缩确实属于本层但可更短的内容 → 抬阈值，且必须在 PR 里为改动给理由。上限是护栏不是缩减目标：在目标以下时保留至少 5% 余量；上限过低是预算 bug，不是文档的错。

## 法则 2 · 门禁即代码，且门禁必须自证

每一条机械可查的约定，都要有一个只拒绝一条不变量、非零退出、错误信息可执行的程序。

一个合格的门禁满足七条：

1. 只拒绝一条不变量。做两件事的门禁在一件失败时给出误导性定位，也无法被单独豁免或单独自证。
2. 非零退出。不靠输出关键词判断成败，不在失败时仍退 0 打印警告——警告等于没有门禁。
3. 错误信息可执行：违规的文件与位置、违规的具体内容、期望形态。
4. 无副作用（除显式的 `--fix` 或 `--write`），默认只读。
5. 确定性：同样输入同样结果，不依赖时间、网络、机器上的可选工具、遍历顺序。缺可选外部工具时明确跳过并说明，不假装通过。
6. 声明它消费源码还是构建产物，两个平面不混。
7. 自证。

**自证的意思是：门禁必须证明它会拒绝。**"在真仓库上跑通了"只证明当前仓库合法；一个写错的正则永远匹配不到东西，在真仓库上永远是绿的，比没有门禁更危险。每个非平凡门禁配一个测试：构造合成的非法输入 → 跑门禁逻辑 → 断言失败并断言错误信息包含定位与原因。同时至少一个合法输入断言通过，防止门禁变成永远失败。

每一条新增或修改的接受规则，都要有对应的非法样例。自证测试断言的是门禁逻辑，不是真仓库状态——写"跑一遍真仓库应该通过"的测试会在任何无关改动上失败，且证明不了拒绝能力。

门禁数量一多就要有编排：一份权威清单（源码或配置）列出全部门禁及分组，文档里不手抄清单；分组按用途（本地精选、CI 全量、需构建产物、需凭证）；任何门禁都能单独一条命令跑；一次跑多个时收集全部失败再统一报告，不是首个失败即中止；调用子进程不经 shell。

## 法则 3 · 生成物防漂移

任何生成的产物——文档、目录、代码、依赖清单、图表——都要有生成器加 `--check` 双模式：生成模式写文件；检查模式在内存里生成、读已提交文件、逐字节比较、不一致即非零退出并提示重新生成。

三条硬性要求：生成器必须确定性与幂等（排序稳定、无时间戳、无绝对路径、无随机 id）；手改生成物一律禁止，文件头写明由哪条命令生成；`--check` 进 CI 门禁组，并属于文档类改动的本地精选组。

这个模式的价值是把"忘记重新生成"从一类反复发生的低级错误变成不可能。

## 法则 4 · 决策记录的生命周期即路径

决策记录是改动者写的 RFC：动机、决定、被击败的备选、后果、验证契约。它不是任务清单、迁移计划的长期归属、变更日志或状态看板。它也不是圣经：记录当时的判断，不是不可推翻的真理。

路径形如 `{生命周期}/{分类}/yyyy-mm-dd-主题.md`，状态既写在文件里也写在路径里，两者由格式门禁互为校验。生命周期为 `proposed`、`implemented`、`rejected`、`archived` 四类。分类取自封闭集合（例如 feature、bug-fix、simplification、architecture、process、testing），加分类要同时改集合与契约文档。`architecture` 关于发布出去的源码，`process` 关于围绕它的工具与流程。

三条硬要求：

- 每个非平凡改动必须在同一个 PR 内新增或更新至少一条记录。更新已拥有该决策的记录即满足，不造重复件。只有纯机械的局部编辑豁免。
- `Alternatives considered` 强制存在。记录一个决策却不记它击败了什么，等于邀请日后重新扯皮。备选只能记录，不能编造。
- 归档即永久冻结：不得编辑、翻译、重排、移动，也不得当作当前行为的依据，由内容哈希清单守护。

骨架固定：三行头部（标题、`Status:`）加 `## Problem` 开头，且 Problem 写成脱离解决方案也能读懂。提案期的标题（`Proposal`、`Plan`、`Migration plan`、`Acceptance criteria`）不得出现在已实施的记录里——那是规划语气。已实施记录用现在时描述已落地的现实，`## Consequences` 记录这个取舍付出了什么、换到了什么。

新增记录时做取代检查：搜索活跃树里覆盖同一决策或机制的旧记录，分为完全取代（归档旧件）与部分取代（保持活跃并互链）。一条记录永远不会被"改成另一个决策"，用新记录取代它。删除一个方向、一种默认值、一个实现，都属于部分取代。

不要建集中索引文件：活跃的生命周期树本身就是清单，索引是又一个会漂移的手抄清单。

## 采纳阶梯

收益随"仓库寿命 × agent 参与度 × 契约面数量"增长。给一次性脚本套全套就是过度工程。按档采纳，不跳档。

| 档 | 适用 | 装什么 |
|---|---|---|
| L1 | 任何会活过一个月、有 agent 参与的项目 | 常驻文件（先不设上限）、决策记录的目录与强制备选段、PR 纪律、阶段取舍档案；门禁只装一个：文档相对链接可达性 |
| L2 | 有 CI、有多人或多 agent 协作、有外部消费者 | 加门禁契约与自证、生成物 `--check`、规则到证据的映射、窄 hook 与 CI 全量分工、散文契约与 slop 清单 |
| L3 | 长期维护的多包或多契约面仓库 | 加字数预算门禁、覆盖率独立门禁与豁免契约、快照录制与重放、文档与代码的漂移门禁、平台矩阵 |

装进门禁时的性价比顺序：文档相对链接可达 → 生成物新鲜度 → 决策记录格式与分类 → 包与模块清单一致性 → 注释里引用的文档路径可达 → 文档里粘贴的类型与源码一致 → 公开导出有文档注释 → 构建产物可被外部消费者解析与运行 → 字数预算。一次只加一个。

## 两条元法则

**现实优于教条。** 测试描述行为，不描述正确性——行为过时就连同它的测试一起改，并在 PR 里说明为什么。任何"因为测试或文档这么写所以必须这样"的论证，都必须先证明该断言仍对应真实需求。

**显式声明阶段取舍档案，连同它的失效条件。** 项目在不同阶段的取舍不同：发布前没有外部消费者时"基础正确性优于兼容性负担"成立，有了消费者就反过来。把当前阶段的取舍写在常驻文件顶部的一节，并在同一节写明何时删除它。失效条件要配检查点：由谁在哪个环节检查它是否已触发、判断产出什么。没有检查点的失效条件等于没写。

## 反模式

- 写了规范但没有程序会拒绝违规。机械可查的必须有门禁；不可机械查的必须写明由谁在哪个环节判断，以及判断要产出什么依据。
- 门禁只在真仓库上跑通就算完成。
- 同一条规则出现在三个文件里。搜索一个特征短语，留一个家，其余改链接。
- 默认跑全套测试来"确保安全"。它掩盖的是"不知道该跑什么"；正确的解法是把改动面到证据的映射写下来。
- 只有结论没有依据的自我审查。凡是标注"由 agent 判断"的检查项，都要产出结论、依据与证据路径。
- 为了让门禁变绿而放宽门禁。抬阈值、加豁免、跳过检查都必须作为独立且有理由的决定被记录；安全相关与发布策略配置永远不为此修改，升级给人类。
- 空壳门禁：项目里不存在该类对象时装一个永不失败的门禁，只会训练所有人忽略输出。
- 让门禁承担判断题。需要语义判断的写进评审标准，并要求判断者产出结论、依据与证据路径。
