# 落地：从工作区到主干

## 动手前先选边界

先只读核对：项目策略、当前分支与基线、未提交改动的归属、其他活动执行者、将触及的文件与共享资源。然后选：

| 情境 | 默认动作 |
|---|---|
| 已在属于本任务的工作分支上 | 继续，并记录位置 |
| 在共享主干上要开始独立功能、重构或有风险的修复 | 写入前建短期工作分支，从相关最新集成基线开始 |
| 另一项工作未结束，或要并行写入 | 独立分支加独立工作区；分支本身不隔离文件、端口、数据库与构建目录 |
| 小型、低风险且项目允许直接提交的文档修正 | 可沿用当前分支；若它改变共享契约，不因是文档就当低风险 |
| 发现有他人或无关的未提交改动 | 保留并识别归属，必要时另用安全工作区 |

有未知或他人改动时，不擅自 stash、reset、搬动、提交或清理；不能假设新建分支就消除了已有改动。影响重要取舍、存在权限缺口或无法安全保留他人成果时才提问。

## 切片

每个 PR 恰好一种性质：功能、缺陷修复、文档、测试、清理。加对应的范围标签；扩展分类集合是一次被记录的决定，不是随手加标签。

独立的改动拆开。混装的 PR 无法被单独回滚、单独评审、单独归因。顺带修掉的无关问题另开 PR，除非它小到"不修就没法完成本 PR"，且在描述里点明。

切片也适用于交付：范围增长或准备并行时，优先拆成可独立验证的小切片；只有在边界、依赖与整合责任清楚、且收益大于成本时才并行。

## 依赖链

有依赖关系的 PR 链用平台官方的栈机制，让平台拥有栈范围的规则、CI、顺序、重定基与合并状态。GitHub 的 stacked pull request 已于 2026-10-06 正式可用（来源：github.blog changelog，核对 2026-10-31）。

不要用"手工合并加改 base"复刻栈语义：手工复刻会在中途状态下丢失顺序保证，且没人能看出真实的依赖关系。

官方栈能力不可用时硬停，不退回手工流程。跨 fork 的依赖链同样硬停——栈通常要求所有分支在同一仓库。独立 PR 与官方栈都可以在评审后 merge-forward 或 rebase；选哪种是有意识的决定，写在 PR 里。

## 历史重写

只用 `--force-with-lease`，永不裸 `--force`。

且要给出期望值：`--force-with-lease=<ref>:<observed-oid>`。git 文档明确指出，不带期望值的 `--force-with-lease` 与任何在后台隐式执行 `git fetch` 的机制交互很差，保护会失效（来源：git-push 手册，核对 2026-10-31）。所以：推送前先取远端当前 OID 并记录，再用它作为 lease。远端已移动时中止，而不是覆盖。

重写会使提交 OID 与行级锚点失效。推送后重新取真实 head，并重新核对未解决的评审线程、批准、可合并性与检查状态。

进行中的 merge-forward 在取用更新的 base 之前，先保住它的检查点。不改 git 配置，不用交互式操作。

## 推送前

1. 确认检出与分支：`git status --short --branch`、`git rev-parse --show-toplevel`。
2. 检查出站 diff 触达了哪些表面。
3. 对触达面跑最小充分证据，一次。
4. 核对实际 diff：范围、意外文件、秘密、契约与断言变化，确认没有夹带或削弱标准。
5. 只汇报真正跑过的命令。

已在某个提交上通过的检查，不因为要提交或推送而重复跑。

## 推送与推送后

推完核对远端 ref 与本地 HEAD 一致：`git rev-parse HEAD origin/$(git branch --show-current)`。

平台 CI 在推送后检查；pending 报 pending。失败先看是实现问题、环境问题还是平台问题，并给出依据。

"没有任何检查上报"时，先读合并状态再加一次空提交：当 PR 处于冲突状态时平台可能根本不创建 workflow 运行，缺信号的原因是冲突而不是基础设施。解决冲突才是修复；空提交、draft 与 ready 来回切换、撤销再恢复，都只会往历史里塞垃圾。

## PR 描述

写"为什么"，不复述"改了什么"——diff 已经说了改了什么。

固定栏目，按顺序：

- **动机**：一句话说清问题，并引用至少一个可解析的 issue 或工作项；只给上下文时用"关联"而不是"关闭"。
- **变更**：分列接口变化与行为变化。接口变化覆盖命令、标志、配置键、环境变量、公开导出、协议与持久化格式；行为变化覆盖用户、模型、开发者与系统能观察到的结果，包括默认值、性能、时序与输出。没有就写"无"。
- **测试**：先给测试设计，再给测试条目。测试设计按变更类型给：行为改变给"场景 × 改前 × 改后 × 覆盖它的测试"；性能改变给前后数值与测量条件（机器、次数、取值方式）；无行为改变的迁移给如何证明行为未变（逐字节比较、未变的快照、新旧对照测试）；纯文档给内容如何被检查。
- **披露**：改了某个已有测试所描述的行为，写明为什么该行为已过时；抬高了阈值、加了豁免、跳过了检查，逐项给理由；把风险或兼容影响写在它所属的栏目里。

只列真正跑过的测试与结果，并标明证据来自本地还是 CI。可评审的证据（输出、截图、日志）放在可折叠块里，长输出可只留命令、计数与结论摘要。

描述写进一个被 git 忽略的文件，再用平台命令以文件为 body 创建或更新；需要附带媒体时用平台的附加机制，不要在正文里粘贴大段日志。

## 多写者与并行 agent

并行写入时，"单写者顺序提交"的默认假设失效：

- 同一文件同一时间只允许一个写者。进入一个文件或目录前声明所有权；发现他人在途改动时不覆盖、不并入，留给原写者或协调后处理。
- 存在未暂存改动时不用 `git add -A`，用显式路径 add，只暂存本次改动的文件——否则会把他人未暂存的修改吞进本次提交。
- 提交前检查未暂存清单，确认本次提交只含自己暂存的内容。
- 并入他人改动时作为独立提交并标注来源，不混在本次改动里悄悄带走。
- 提交信息聚焦"为什么"；提交前检查是否含敏感信息；提交前钩子改了文件导致失败时，把被改文件重新加入暂存区再重试，不绕过钩子；没有改动就不制造空提交。

## 授权的边界

未被明确要求时不推送、不合并、不发布。

不可逆或高成本的动作——合并到主干、生产部署、打版本标签、发布制品、发邮件、调用有真实副作用的接口——需要针对该具体动作的显式批准；之前的批准不自动延伸到新动作。

请求批准时给决策简报，不是执行日志：证据留在文档、PR 与测试输出里，简报只引用路径；机器已确认无问题的项一行汇总；只展开有风险的、需要取舍的、以及自己拿不准的；每个待定点附建议答案与理由，让人类可以只回"按建议走"。

## 结束前

- 远端 head 与本地一致，CI 状态如实报告。
- PR 描述与实际 diff 一致，没有列出未跑过的证据。
- 依赖链仍在预期顺序上，被重写的层都重新验证过。
- 分支删除只在对应 PR 确认合并后，且没有其他未关闭的 PR 仍以它为 base。
