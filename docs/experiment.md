# 一轮改进记录（v1 → v2）

## 方法

按改进回路的轻量形态跑：**立基线 → 定判据 → 量 → 归因 → 改一处 → 重量 → 冠军线**。

限制先说清：没有可观测的加载轨迹（无法在新会话里实测「哪份被激活」），所以触发相关的判据用人工按描述判定，机械部分用脚本计数。这意味着判据 4 的结论是判断，不是实测。

- 基线：v1，按材料直接归拢出来的版本，7 份正文合计 785 行，0 份 references，冻结在 `docs/v1/skills/`，未改动。
- 候选：v2，即 `skills/` 下的现行版本，7 份正文合计 754 行，16 份 references 合计 1098 行。
- 一轮里改了 5 处（每处对应一条判据），未做第二轮。

## 判据

选 5 条，前 4 条可数或可指，第 5 条防「局部变好、整体变薄」。

| # | 判据 | 怎么量 | 合格线 |
|---|---|---|---|
| 1 | 描述先触发后能力 | 7 份描述中「首句是触发条件从句」的份数 | 7/7 |
| 2 | 跨 skill 重复的规则条数 | 预定义 5 条规则中，以完整规则表述出现在 ≥2 份正文的条数 | 0 |
| 3 | 渐进披露 | references 份数、带「读它的时候」的比例、正文最大行数 | 细则有去处、每份 ref 有读触发、正文 ≤200 |
| 4 | 触发区分度 | 8 条真实请求中，读完描述会命中 ≥2 份的条数 | ≤1 |
| 5 | 主题覆盖 | 材料里 21 个主题中，正文有可执行落点的数量 | 21/21 |

判据 2 的 5 条预定义规则（先定义，再计数，两版用同一份定义）：

1. 「每个改动跑最窄证据，一次」
2. 「只报告真正跑过的证据」
3. 「证据必须能失败（负控/自证）」
4. 「一个事实一个家」
5. 「授权覆盖与证据覆盖分开核对」

**计数口径**：一条规则以**完整表述**（含条件、理由或多条子规则）出现在两份及以上正文，计 1 条重复。一句话的应用（例如「跑覆盖这些表面的证据」）不计入——不然任何提到同一动作的句子都会被算成重复，两版就不可比了。

判据 5 的 21 个主题：阶段推进条件、输入分流、三种结论与授权复用、变更传播、记录与状态、证据与验收、交付与恢复、评审流水线、发现核验与轮次、风险分级与审批、常驻分层与预算、门禁契约与自证、生成物防漂移、决策记录、散文契约、失败设计、证据选择与确定性、落地与栈与强推与 PR 描述、工程准备、装进已有项目、性能证据、语句效力五类。

## 归因：每条判据改了哪一句

### 判据 1 —— 改的是 7 个 `description` 的第一句

v1 的第一句一律是能力，例如 `review-gate`：「组织一次代码或文档变更的评审与审批：安排独立的发现视角、核验发现…」。v2 把它换成触发：「当你要评审一个 PR、被要求「审查一下这个改动」、要判断一处发现算不算阻塞…时使用本 skill」，能力句后移，末尾加一句判定。

实测：7 份描述长度 151–189 字符，判定句起点在 117–156 字符之间，都落在宿主可能截断的 500 字符以内。

### 判据 2 —— 删掉或收窄了 5 处

| 位置 | 改法 |
|---|---|
| `change-landing` 推送前第 3 步 | 「跑最小充分证据，一次」→「跑覆盖这些表面的证据」（去掉规则名与重复的「一次」） |
| `change-landing` PR 描述 | 「只汇报真正跑过的命令」→「只列已完成的测试及其结果」（改为动作，不再复述规则） |
| `failure-handling` 验证段 | 「负控：故意注入一个预期失败，确认报告出现」→ 删掉「负控」框架，改为「注入一个预期失败，确认报告出现、状态符合声明的保证级别、失败没被吞成成功」——它验证的是报告，不是检查能力 |
| `contract-prose` 审计清单 | 整条删除「同一条规则有两个以上的家」。归属判断归 `engineering-standards`，此处只保留「理由抄在并列成员旁边」这种文字级重复 |
| `review-gate` 风险段 | 删掉整段「授权覆盖与证据覆盖分开核对」，只留一行「方向决定不自动覆盖新提交」，把原理留给 `delivery-loop` 的五项复用检查 |

另有一处同源重复一并删掉：`review-gate/references/risk-routing.md` 里的决策简报模板与正文的「请求决定时包含五项」内容重叠，删除模板，保留正文。

### 判据 4 —— 没有改，打平

8 条请求里只有一条歧义：「这次改完了，推之前该跑哪些测试」。它同时命中 `change-evidence`（推送前取舍检查范围）与 `change-landing`（要提交、推送）。两版都是 1/8。

按冠军线，这条判据打平就不动。想消除它只有一条路：把 `change-landing` 的触发从「推送前」收窄到「落地动作」（提交、改写历史、合并、写描述），但那样可能让「我该推这个分支吗」这类请求掉出去。这轮不动，登记为已知的近邻重叠。

### 判据 5 —— 补了 4 个覆盖缺口

第一版是「按材料归拢」的产物，归拢时会不自觉地跟着材料的篇幅分配注意力，于是漏掉了四块：

| 缺口 | 补法 |
|---|---|
| 工程准备（当期能力与能力自证） | `delivery-loop` 正文加一段 + `references/readiness.md`（能力五项、只补当期缺口、受控坏样例、入口与负责人、缺口记法） |
| 装进已有项目（判档、扫描、安装顺序、审计） | `engineering-standards` 正文加指针 + `references/adoption.md` |
| 性能证据 | `change-evidence` 正文加「性能改动的证据」一节 + `references/performance.md` |
| 语句效力五类（要求/决定/事实/假设/提议） | `contract-prose` 正文加一张表 |

这四处都是从 devloop 的 `phase-test-infra`、`documentation`、`migration`，deep-standard 的 `adoption`，以及 `dsh-speed-up-perf` 里来的——v1 读过 `dsh-speed-up-perf` 却没有给它落点，属于归拢时的遗漏，不是判断。

## 冠军

**v2**。五条判据里四条严格更好（+7、−5、+16 refs、+4 主题），一条打平（1/8）。回归项全部保持通过。

回归账本（v2 仍须保持，下一轮改动前先重跑）：

- `skills-ref validate` 7/7 输出 `Valid skill`。
- 删掉 `description` 后校验必须失败（已做，见下）。
- `name` 与目录同名；只用六个顶级字段；`metadata.face` 每份一个。
- 正文 ≤200 行（当前最大 124）。
- 每份 references 都有「读它的时候」。
- 任何正文与 ref 不提其它 skill 的名字。

校验与负控的实际输出：

```
$ skills-ref validate skills/<each>   →  Valid skill（7/7）
$ 删掉 failure-handling 的 description 后重跑
  Validation failed for .../failure-handling:
    - Missing required field in frontmatter: description
$ 恢复后重跑  →  Valid skill
```

## 三条可复用的观察

1. **体量判据会骗人。** 判据 3 单独看是「没进步」：正文 785 → 754，只少 31 行。原因是抽取细则腾出的空间立刻被补覆盖缺口吃掉（抽出后一度到 727，补完覆盖缺口又回到 754）。真正变的不是字数，是**细则的可达路径**：从「每次激活都读」变成「需要时读」。所以体量类判据必须配一条分布类判据一起看。
2. **打平的那条往往指向词而不是句子。** 判据 4 的歧义来自「推送」这个词同时属于两个动作，不来自语序。改词序没用，改触发范围才有用，而那是高风险改动。打平就保留旧的，别为了让它变绿而制造新风险。
3. **机械计数需要先定义什么算一次重复。** 用 grep 数「同一短语出现在几份文件里」，会把「一句话的应用」也算成重复。先写清口径（完整表述 vs 应用），两版才可比；口径本身要写进记录，否则下一轮会用它自己都说不清的方式度量。

## 仍未解决

- 判据 4 的 1 条歧义（推送前跑测试）。
- 没有真实加载轨迹：触发判断是人工按描述做的，不是实测命中率。按方法要求，这属于「没有可观测轨迹时退回冒烟」，而冒烟本身也没做——需要一次真实的新会话安装与观察。
- execution 面的结构性空白（环境搭建、可观测性、发布工程），见 `docs/plan.md`。
- 判据 2 只覆盖预定义的 5 条规则；不排除还有未被纳入计数的重复（尤其是「变更故事的家」「先读再判」这类跨两份出现的判断）。

## 外部对照：两轮同题实验

用两个互不知情的 agent、同一输入、只差可用材料。

### 第一轮：审一段 85 行 diff（埋 5 个问题）

| | 基线（23 份原始材料） | 处理组（本 set） |
|---|---|---|
| 命中 | 6/6 | 6/6 |
| 误报 | 无 | 无 |
| 阅读 | 9 份 / 677 行 | 9 份（5 skill + 4 ref） |
| 额外产出 | — | 风险分级与审批路由 |

**打平。** 质量面的判断力没有增益——原始材料里的 `code-review` / `gates-as-code` / `evidence` 三份被基线精准挑中，就够用了。

### 第二轮：为一个 63 行 CLI 写实施计划（三个面都要用）

| | 基线 | 处理组 |
|---|---|---|
| 计划行数 | 167 | 336 |
| 阅读 | 12 份 / 1319 行 | 7 skill + 4 ref |
| 验收条件 | 15 | 12 |
| 测试 | 6 层验证 | 21 条，每条标注"在 0.3.0 上会失败/通过"（负控） |
| 落地 | 1 个 feature PR + 后续 bug-fix | 4 个 PR 按性质拆，含依赖序、逐 PR 风险/审批/回退 |
| 人决定点 | 3 + 5 可延后 | 10（含"这个目录不是 git 仓库"的硬前置） |

**处理组在流程与落地上更完整**，代价是两倍篇幅。

### 由实验发现的一处蒸馏缺陷

处理组把一次 63 行改动拆成 4 个 PR、写 336 行计划——而源材料 devloop 明确有"小型低风险修正按项目许可简化""微小确定性改动可有据裁剪"，这两条在蒸馏时**丢失了**（`delivery-loop` 里零命中）。没有"按规模裁剪"的约束，流程只会朝更严的方向单调加码。

已在 `delivery-loop`（流程深度与改动规模成比例）与 `change-landing`（切多细看爆炸半径）各补一条。

## 第三轮：把计划交给实现 agent 执行

用第二轮处理组那份 336 行的计划，在一个带 0.3.0 基线提交的仓库副本里真的实现：四个分支、四个提交、34 条测试全绿；同一套用例在 0.3.0 源码上跑出 12 pass / 22 fail（通过的正好是 11 条回归钉 + 原单测），成功路径 12/12 用例逐字节一致。

### 计划骨架成立，但内部有 16 处问题，其中 4 处自相矛盾

1. 计划说「这不是 git 仓库」——副本已经有基线提交，照做会毁基线。
2. 步骤 1 的 `{ json, paths, stdinRequested }` 无法表达 argv 顺序，而冻结的并列排序规则正需要它。
3. 「入口改成 async」与「stderr 逐字节一致」不可同时成立——未捕获栈里含源码路径与行号。
4. 步骤 2 的「预校验路径存在」与冻结项「二进制后缀先跳过」冲突：`tally missing.png` 在 0.3.0 是 exit 0，预校验会把它变成 exit 1。
5. 用例 T12 与 D3 直接矛盾：`-` 归 `(none)`，与 `.ts` 必然两行，不可能合并成一行。

另有：T21 按计划给的断言在旧版本上本来就会通过；`npm pack` 冒烟测不到 `bin` 映射，真实安装后 `node_modules/.bin/tally` 因缺 shebang 直接失败（0.3.0 就存在，计划范围外）。

### 结论

**写得很细不等于想得很对。** 计划在文档层面自洽，矛盾只有在执行时才暴露；而这些矛盾没有一条是这套 set 的判据能提前发现的——因为判据检查的是「有没有写」，不是「写下的东西彼此是否成立」。

已据此在 `change-evidence` 补一条：计划里的「新证据」必须逐条在旧版本上真跑，标注与实际不符说明计划有矛盾，先修计划再实现。
