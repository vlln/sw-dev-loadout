# 实验：同一任务的四次产出

同一条任务——"为一个真实插件仓库重写 README，不许看现有 README"——跑了四次，唯一变量是方法与 skill 版本。夹具与原文见 [runs/](runs/)。

度量口径（2026-11-01 按保存的原文重数）：行数不含末尾空行；`##` 只数二级标题；表格行数所有以 `|` 开头的行，含分隔行；代码块数围栏对数；徽章单独计，不计入图片。

| 版本 | 方法 | 行数 | `##` | 表格行 | 代码块 | 徽章 | 图片 |
|---|---|---|---|---|---|---|---|
| A 基线 | 无 skill | 354 | 15 | 98 | 10 | 0 | 3 |
| B 带 v0.1.0 | 本文 skill 初版 | 372 | 10 | 21 | 25 | 2 | 2 |
| C 带 v0.2.0 | 本文 skill + 三条修正 | **148** | **7** | — | — | — | — |
| D 带 v0.2.0 + 高星项目风格 | 同一 skill，模仿一个高星项目的排版节奏 | **140** | **7** | 14 | 3 | 2 | 6 |

C 的原文没有保存，除行数与节数外无法重数；原先那张表里 A/B/D 的图片、代码块、表格行有几格与原文不符，已按上面的口径改正。这正是"度量口径要先写下来"这条要求的由来——没有口径，同一份产出会被数出不同的数。

## 结论

1. **初版只改了"排法"，没改"排多少"。** B 有了徽章、可复制安装块、首屏纪律（源码引用从 15 降到 8），但 372 行、10 节，与基线同量级——它仍然是手册。
2. **加了三条规定之后，体量被压住了。** C 从 372 压到 148，仍保留安装、快速开始、面板、命令、限制、文档、许可；被压出去的是 `ctx` 原语、确定性规则表、门禁断言数、15 条限制里的 7 条、本地开发流程。
3. **可执行的判据才有效。** "首屏只回答这是什么""安装块必须能原样跑""不搬测试数字"在 B 就被执行了；"别写太长"在 B 里根本不存在，于是没发生。

## 三条修正（v0.2.0）

- 体量判据：≤150 行、`##` ≤8，并给出超标时的处理顺序。
- 读者表加"在哪一屏"一列，落在"深处"的默认链接走。
- 新增自检 18–20：无实现者段落、在体量内、至少一条命令可原样跑通。

## 代价

- C 丢了音频制作流程，且没有可链接的去处（包内脚本没有干净的 CLI 入口）——这条缺口是仓库文档的问题，不是 README 的取舍。
- C 与 B 都放弃了基线的"适合 / 不适合"自选表；那是基线自己想到的，skill 没有要求。

## 由此补的一条规则

搬走的内容必须在 README 里留一处链接；没有去处，说明那份文档该补上，而不是可以不写。

## 第四版：风格模仿被预算约束住

D 是同一份 skill、同一个仓库，但要求参考一个高 star 项目的写法。那个项目是 200+ 行、十几个 `##`、每节一张图、还带语言切换。

结果：**取了节奏，没取体量**——首屏换成整幅截图 + 居中定位句 + 居中徽章，中段拆成四个"一句人话 + 一张真图"的 feature block，限制收进 `<details>` FAQ；行数 148 → 140，节数仍是 7。

这说明体量判据不只是"砍字"：它把"模仿"从"照抄结构"逼成"选择哪些块值得留"。代价是 D 丢掉了基线里那张"适合 / 不适合"自选表——产品化的首屏更容易吸引到期待 GUI 剪辑器的人，而 FAQ 里只答"要装什么"，没答"你不该用"。

图片核对：D 引用的 6 张图全部是仓库既有文件（2026-10-27），单张 40–108 KB，GIF 1.5 MB（5 秒），都在 skill 的体积上限内；仓库 `git status` 干净。

## 这些结论有多硬

- 四个版本各只跑了一次，没测同一夹具重跑的波动；"372 → 148"说明方向，不是效应量。
- C 版原文没留存，它只剩两个数字，没法复查。
- 只用了一个夹具（一个 dsh 插件仓库）。"体量判据有效"这条结论还没在第二类项目上复现过。
- 没有实测触发命中率，也没做新会话冒烟。

## 第五条证据：体量判据没能在第二类读者上复现（2026-11-01）

上面写了"只用了一个夹具，体量判据还没在第二类项目上复现过"。复现来了，结果是**否定性的**：

`woniuniuniu/dsh-media-desk` 的 README（用户判定为"几乎最佳"的范本，2026-11-01 读源码量化）：269 行、12 个 `##`、4 枚徽章、6 组配图全部深浅色成对、7 处居中块、17 个 `<br>` 隔节。按当时的 skill 判据（≤150 行、≤8 节、徽章 1–3），它三条全违。

它不是绕过了规则而成功，是规则管不到它的读者：那是一份给**最终用户（非开发者）**看的产品页，这类读者的决策路径是"好看 → 可信 → 敢装"，一个功能一节一图是主内容而非装饰，价格 / 数据去向 / 卸载 / 作者是决策输入而非冗余。

修正（v0.4.0）：规则补上**读者轴**。150/8 上限与克制默认保留给开发者向（本实验的 354→148→140 证据在开发者工具上仍然有效）；最终用户向换成"每节都要能说出回答读者哪个问题"。新增一致性规则（徽章同 style 同色系、图同宽、深浅成对、节间节奏）与海报式首屏写法。

教训正是 `skill-writing` 自己那条：**每条"必须"都要能说出它的适用条件**。体量判据此前说不出适用于谁，于是默认自己适用于一切。
