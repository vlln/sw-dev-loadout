# 触发测试：10 条真实请求

**怎么判的**：逐条读 `SKILL.md` 的 `description`，问"这句描述是否覆盖了这条请求要的东西"。每条给出承担判断的那句描述文字。本会话无法观测宿主的加载轨迹（看不到 skill 是否被注入上下文），所以下表是**文本判定**，不是加载记录；若要拿到真实命中率，需在装好 skill 的会话里对新请求各跑 3 次，看加载轨迹。

`description` 里承担判断的四句，下文用 A–D 指代：

- **A**：当要写、重写或审一份项目 README（GitHub 仓库首页、开源项目主页、npm / PyPI 包页面上那份说明）时使用本 skill
- **B**：按读者分层排出信息层级，决定徽章、logo、截图 / GIF、表格、折叠区用不用、放在哪
- **C**：找出工程细节混进正文与排版凌乱的问题
- **D**：产出对标高 star 开源项目的 README：先服务读者，后服务实现者（英文镜像：writing / rewriting / reviewing a project README）

## 应触发（6 条）

| # | 请求 | 预期 | 承担判断的描述文字 |
|---|---|---|---|
| 1 | "仓库刚开源，README 还是脚手架生成的，帮我重写一份能看的" | 命中 | A 的"重写……一份项目 README"——动词与产物都在描述里 |
| 2 | "README 太长，新人进来找不到安装命令，帮我重排信息层级" | 命中 | B 的"按读者分层排出信息层级" |
| 3 | "帮我审一下这份 README，排版很乱，还塞了很多实现细节" | 命中 | A 的"审一份项目 README" + C 的"工程细节混进正文与排版凌乱" |
| 4 | "给我的 npm 包写 README，要有徽章、安装、用法和截图" | 命中 | A 括号里的"npm / PyPI 包页面上那份说明" + B 的"徽章……截图 / GIF" |
| 5 | "我们的项目主页没人看得懂，装之前不知道这工具是干嘛的" | 命中 | A 括号里的"开源项目主页"——不用说出 README 两个字也能落点 |
| 6 | "review my README — it reads like an engineering log" | 命中 | 英文镜像的"reviewing a project README" + C 的"工程细节混进正文" |

## 不应触发（4 条近邻）

| # | 请求 | 预期 | 为什么不该命中 |
|---|---|---|---|
| 7 | "把这个项目的 CHANGELOG.md 按 Keep a Changelog 重排" | 不命中 | 描述里的产物只有 README；`changelog`、版本历史这类词不在描述中。这是最险的一条：正文提到"变更流水应搬进 CHANGELOG"，容易让判读者以为覆盖面更大，但判据只看描述。 |
| 8 | "补一份 CONTRIBUTING.md，写清分支模型和提 PR 的规矩" | 不命中 | 描述里没有贡献指南、CONTRIBUTING、协作流程这类锚点；读者分层表里的"想贡献的人"只是 README 内部的一节，不扩大触发面。 |
| 9 | "把 src/ 下的函数补上 docstring，再生成 API 文档站" | 不命中 | 描述里的"用法、API"只是 README 里的一节，能力是"写 README"，不是"写 API 文档"。请求里没有任何 README 产物。 |
| 10 | "给这次发布写 Release Notes，按新功能 / 修复 / 破坏性变更分组" | 不命中 | 同 #7：发版说明是另一种产物，描述未覆盖；"工程细节"判据针对的是 README 正文，不是通用写作。 |

## 结论

- 应触发 6 / 6，不应触发 4 / 4（文本判定）。
- 真正需要观察的边界是 #7 与 #10：它们与 README 共享"文档取捨"这个判断，但产物不同。若装好后实测这两条被误触发，先改的应是描述的产物限定（A 的括号），而不是加否定句——否定式的近邻说明会让描述变长且更易误命中。
- #5 是反向验证：描述里显式写了"项目主页"这个同义说法，所以用户不必说出 README 也能命中。
