# 第四轮：换夹具复验三条规则

夹具 `envcheck` 0.2.0（Python 标准库，85 行，9 用例全绿），需求四条小改动。两个互不知情的 agent，同一输入同一任务，只差"给不给这套 skill"。预测写在动手前（见 `docs/runs/r4-predictions.md`），结果出来后未改动。

两组都：三到四个提交、测试全绿、受保护输出逐字节不变（我独立 `cmp` 核对过成功路径与缺失明细，两组对 0.2.0 都是 BYTE-IDENTICAL）。质量面再一次没有差别，与前三轮一致。

| | 基线 | 处理组 |
|---|---|---|
| 计划行数 | 261 | 194 |
| 提交数 | 4 | 3 |
| 用例数 | 21（新增 12） | 22（新增 13） |
| 新增用例在 0.2.0 上失败 | 8 / 12 | 9 / 13 |
| 计划里逐条标注"旧版本会怎样" | 0 处 | 全部 13 条 |
| 打标签 | 打了 `v0.3.0` | 没打（"提交、打标签、发布是三个独立授权动作"） |

## 规则 B（新证据必须在改动前的版本上真跑一遍）：复现，且抓到一个真缺陷

处理组的计划给每条新用例预判了基线结果，并把其中 4 条标为"基线通过 ⇒ 不得当作新行为的证据"。我把它的测试文件拿到 `ddee27b` 的 worktree 上实跑：**22 跑 9 败，逐条与它的预判一致**，包括夹具里埋的那条（`cannot read` 的消息在 0.2.0 上本来就带 rc 路径，所以为需求 4 写的这条用例在旧版本上就是通过的）。

基线组最终也做了旧版本对照，而且做得很硬（detached worktree + `cmp`，还把 `v0.2.0` 的测试文件当外部裁判跑，9/9 通过）。但那是**实现时的补救**：它自己的报告写明计划里原本的两个方案"不够硬""是循环论证"。处理组是**计划阶段就要求**逐条标注。

差别不在"最后有没有做对照"，而在"这件事是计划要求的，还是撞上了才补的"。而且后者漏了东西：

**基线的 12 条新用例里有 4 条在 0.2.0 上通过，其中 2 条是真的漏网。**

- `test_quiet_and_rc_order_independent` 是需求 2（顺序无关）的**唯一**用例。它断言两种顺序的 returncode / stdout / stderr 三者相等——而在 0.2.0 上两种顺序都以 `unexpected argument '--quiet'` 退 2，三者确实相等，于是通过。它漏了"还得成功"这半句。处理组的同名用例多一行 `assertEqual(after.stdout, "2 of 2 required variables missing\n")`，于是在 0.2.0 上失败。
- `test_unexpected_argument_after_quiet_exits_two` 在 0.2.0 上通过，因为 `--quiet` 自己就是那个"未知参数"。

另 2 条（注释里的 `=` 可接受、空格错误优先于 `=`）是合法样例守卫，本来就该通过——但基线没有区分这两类，它不知道自己哪条是守卫、哪条是漏网。

这正是第三轮那条规则的原文所预言的形态，换一个夹具、换一种语言又出现了一次。**按改进回路的要求，规则 B 从候选升为确认。**

## 规则 A（流程深度与改动规模成比例）：测不出，仍是候选

第二轮那次过度流程（63 行改动 → 4 个 PR / 336 行计划）没有重演：处理组 3 个提交、194 行计划，比基线的 4 个提交、261 行计划还短。

但这不能算规则 A 生效，因为**基线同样克制**。任务小到两边都不会过度，对照就没有分辨力。这是夹具设计的失误：为了验"按规模裁剪"而刻意选小任务，恰好消掉了能看出差别的条件。要验它需要一个大到有拆分诱惑的夹具。

处理组确实留下了可观察的裁剪表态——`§9` 写"不再往下切（不把 docstring、测试、实现拆成三个提交）——那是把配额当纪律"，`§7` 一整张"明确不做"表，含放弃给 85 行仓库装 `AGENTS.md`、决策记录目录树与文档门禁（理由是 `engineering-standards` 的空壳门禁反模式与采纳阶梯只到 L1）。基线没有这类表态，但行为上一样克制。**有表态不等于有差别。**

## 规则 C：不在这套 set 里，但缺口被另一条规则盖住了

需求 4 说"所有退出码 2 的错误信息都必须带 rc 路径"，而 `--rc` 后漏参数这条路径上根本没有路径可带。这是夹具里第二处埋点。

- **处理组**：计划里写明"**这是本条唯一不满足的点，且不可满足**——填默认值 `.envcheckrc` 会是一句假话（工具根本没打算读它）"，保持原消息，并要求在报告里列为"需求字面未满足项，不悄悄算作完成"。起作用的是 `contract-prose` 的"诊断必须指向真实的失败主体"。
- **基线**：给它填上 `(rc: .envcheckrc)`，理由是"本来会用的那份配置""一条规则到底就不可能漏"。推理完整，不是疏漏；但结果是工具报出一个它从未打算读的文件名。

需要说清楚：那条"规则之间不得互相矛盾"写在另一个仓库的 `skill-writing` 里，**没有给处理组**。这七份里没有任何一条要求"动手前先检查需求自身是否自相矛盾"。所以这一处不是规则 C 的复现，而是 set 的一个缺口恰好被 `contract-prose` 盖住了。盖住它的是"诊断要真"，不是"需求可能自相矛盾"——换一个不涉及诊断文本的矛盾需求，这套 set 还是会直接照做。

## 一处我自己的错误

我在核验基线组"把 v0.2.0 的测试文件当外部裁判"这一说法时，先把那个文件复制到 `/tmp` 下跑，得到 5 个失败，差点据此判它说法不实。原因是那个测试文件用 `__file__` 算 `ROOT` 并以此设 `PYTHONPATH` 与 `cwd`，搬出仓库后算出的根目录是错的。放回仓库 `tests/` 下跑是 9/9 通过，它的说法成立。

教训与规则 B 同源：**对照实验的执行环境本身也要先验一次**，否则测的是环境而不是对象。

## 这一轮能说什么

- 规则 B 在第二个夹具上复现，升为确认。它抓到的是一条真缺陷，不是风格差异。
- 规则 A 这一轮无效，夹具选错了，仍是单夹具候选。
- set 缺一条"需求自身可能不可满足"的规则；这一轮它没造成损害，但原因是运气。
- 仍然：每条只跑一次，出题与答题是同一个模型，没有实测触发命中率。样本从 1 变成 2，不变成统计。
