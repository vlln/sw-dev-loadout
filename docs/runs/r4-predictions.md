写于 2026-11-01，两个 agent 已启动但尚未返回任何结果。目的是防止事后合理化：结果出来后只能对照这份文件判对错，不能改这份文件。

## 夹具

`envcheck` 0.2.0，Python 标准库，两个模块共 85 行，9 个用例全绿。与前三轮的夹具在语言（Python vs Node）、规模（85 行 vs 63 行 CLI / 85 行 diff）、任务性质（四条小需求 vs 一次功能新增 / 一次评审）上都不同。

需求四条，刻意都很小：加 `--quiet`、flag 顺序任意、rc 里带 `=` 的行报错退出 2、所有退出 2 的信息都要带 rc 路径。

## 夹具里埋的东西（已在 0.2.0 上实测确认）

1. **`cannot read` 这条信息本来就带 rc 路径。** 需求 4 说"所有退出码 2 的错误信息都必须带上 rc 文件的路径"，但 `--rc /nonexistent/x.rc` 在 0.2.0 上已经输出 `envcheck: cannot read /nonexistent/x.rc: ...`。为这一条写"旧版本会失败"的负控，实测会通过。
2. **两条退出 2 的路径上根本没有 rc 路径可带。** `--rc` 缺参数、`extra` 多余参数，这两种情况发生在读 rc 之前，`rc_path` 要么还是默认值要么无意义。需求 4 的字面要求在这两条上不可满足，需要判断并提出来，而不是硬套。
3. **`A=1` 这种行今天被当成变量名原样接受**，输出 `missing: A=1`，退出 1。需求 3 要把它变成退出 2——这是真的行为变更，负控会真的失败。

## 三条待验规则

每条都只被一个夹具逼出来过，这一轮看它们在新夹具上是否复现。

### 规则 A：流程深度与改动规模成比例

来源：第二轮。当时处理组把 63 行 CLI 的改动做成 4 个 PR、336 行计划，而源材料里"小型低风险修正按项目许可简化"这条在蒸馏时丢了。补进了 `delivery-loop` 与 `change-landing`。

**预测**：处理组这次给出 **1–2 个提交**、计划 **≤120 行**，并且会显式说一句"这次规模小，所以不拆成多个 PR / 不走完整流程"。

**判为失败**：仍然 ≥3 个提交，或计划 ≥200 行，或虽然规模小却逐项走完所有流程动作而没有任何裁剪表态。

### 规则 B：新证据必须在改动前的版本上真的跑一遍

来源：第三轮。当时计划里标注"这条在 0.3.0 上会失败"，实测有的本来就通过。补进了 `change-evidence`。

**预测**：处理组会对需求 4 做负控时发现 `cannot read` 这条**本来就通过**，并明确记下来（而不是写"旧版本会失败"）。

**判为失败**：处理组声称所有新用例在 0.2.0 上都会失败，却没有实测；或实测了但没发现那条本来就通过的。

### 规则 C：规则之间不得互相矛盾 / 规则要带适用条件

来源：第三轮（4 处自相矛盾）。这条补进的是 `skill-writing`，约束的是写 skill 的人，但它在这一轮的对应物是：**计划自己能不能发现需求 4 在两条路径上不可满足。**

**预测**：处理组在计划阶段就指出需求 4 与"`--rc` 缺参数""多余参数"这两条路径冲突，并给出处理方式（缩小需求范围，或说明为什么这两条例外）。

**判为失败**：照抄需求 4 的字面要求，实现时才撞上，或者干脆给这两条硬塞一个无意义的路径。

## 对基线组的预期

基线组没有这套 skill。预期它在**质量面**上表现相当（前三轮已反复证明判断力无增益）：它很可能也会发现 `A=1` 的行为变更，也会把测试写对。

**真正的对照点**只有三个：

- 它会不会做负控、会不会实测旧版本（规则 B）；
- 它会不会提前发现需求 4 的不可满足路径（规则 C）；
- 它的提交数与计划体量（规则 A 的参照系——如果基线也是 1 个提交 120 行，那"按规模裁剪"这条就不是 skill 的贡献，而是任务本身简单）。

**规则 A 的判定必须靠基线做参照。** 这是第二轮没做对的地方：当时只看处理组 336 行就说它过度，但没有"同样规模下基线写多少"的对照。

## 这一轮能证明什么、不能证明什么

- **能**：三条规则在第二个夹具上是否复现。两个夹具都出现，按改进回路的要求就从"候选"升为"确认"。
- **不能**：仍然是同一个模型在出题和答题；仍然每条只跑一次；仍然没有实测触发命中率。样本从 1 变成 2，不变成统计。

## 补记（仍在 agent 返回之前写下）

**规则 C 的归属弄错了，这一轮测不到它。** 复查后：那条"规则之间不得互相矛盾"写在 `skill-writing` 里，而 `skill-writing` 属于 `skill-loadout` 仓库，**没有给处理组**。处理组拿到的七份里没有任何一条要求"动手前先检查需求自身是否自相矛盾"：

- `change-evidence:107` 管的是"标注与实际不符"，只覆盖证据标注，不覆盖需求本身；
- `delivery-loop:72` 与 `change-control.md:22` 管的是"接入已有项目时不留两套矛盾规则"，是变更控制，不是需求审查。

所以规则 C 这一轮**不是在验它复现，而是在验这套 set 有没有这个缺口**。

修正后的预测：**处理组很可能也会撞上需求 4 的不可满足路径，而且很可能和第三轮一样是在实现时才撞上，不是在计划阶段。** 如果两组都在实现时才撞上，说明这是 set 的一个真实缺口，该补一条规则；如果处理组靠 `review-gate` 的"先读要求再判"提前发现了，那是意外收获，要指出是哪一句起的作用。
