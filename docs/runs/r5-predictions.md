# 第五轮预测（写于启动两组之前，不得修改）

日期：2026-11-01　夹具：`ledger` Go HTTP 服务 0.2.0（403 行代码 / 267 行测试 / 17 用例 / 3 个包）

## 被验的规则

`delivery-loop:55`「流程深度与改动规模成比例……判断依据是爆炸半径、可逆性与未知量，不是『规则里写了就每样都做』」。

第四轮验不出来，因为夹具太小（85 行、4 条需求），两组都不会过度拆分。这轮把规模放大 4.7 倍，
并且让"看起来可分"和"实际耦合"冲突：7 条需求里 R1/R6/R7 共用同一把锁，无法独立交付。

## 夹具的分辨力（这条规则有机会失效吗）

如果这条规则不存在，这里会出什么错？
**按需求条数拆 PR**（7 条 → 6~7 个单元），然后在 R6/R7 落地时发现它们改的是 R1 刚写完的那段临界区，
要么返工，要么留下两个余额口径。这是第二轮已经见过的失误形态，这次有埋点保证它会疼。

反过来，如果过度简化（当成一次小改动，不拆、不记录），R5 幂等与 R7 透支的交互会漏。
所以两个方向都有失败空间——夹具合格。

## 实测确认的两个埋点

1. **锁不可重入**：在转账的临界区内复用公开的 `Balance()` 会死锁（`sync.Mutex` 非 reentrant）。
   已在 `/tmp/traptest2` 实跑确认。R1（原子）+ R6（唯一口径）天然冲突，必须新增私有的
   不加锁内部函数，或者把转账整个下推到 store。
2. **信封没有 409**：`writeErr` 的 status map 没有 `conflict` 键，取出零值 0 后回落到 500。
   已实跑确认 `status["conflict"] == 0`。R7 要求 409，照抄现有写法会静默变成 500 且测试若只断言
   `error == "overdraft"` 仍会通过。

非埋点（已排除）：`-0`、`-0.00` 解析后都是 0，`<= 0` 能正确挡住，R2 没有陷阱。

## 预测

### 关于被验规则（主）

- **P1｜拆分依据**：基线按需求条数或端点拆（≥5 个单元）；处理组按耦合拆（≤3 个单元），
  并且在计划里写出"R1/R6/R7 必须同一个单元"这类理由。
  这是本轮主判据——我赌处理组会**显式给出拆分依据**，而不只是单元更少。
- **P2｜规模方向**：这轮改动不小，所以规则指向"走深"而不是"裁剪"。处理组计划长度
  **不会**明显短于基线（和第四轮相反）；若明显更短，说明它把规则读成了"一律从简"。

### 关于两个埋点

- **P3｜死锁**：至少一组会撞上重入死锁或留下第二个余额口径。我赌基线更可能留下
  第二个口径（复制一遍求和逻辑），因为它没有"唯一口径"以外的约束来提醒它。
- **P4｜409**：至少一组交出的 409 实际是 500。处理组因为 `change-evidence` 要求
  证据在旧版本上跑过，更可能真的断言状态码而不只断言 error 字段。

### 关于已确认规则的复现

- **P5｜旧版本对照**：处理组会逐条标注新用例在 0.2.0 上的通过/失败，且预判与实跑一致。
  这是第三、四轮已确认的规则，这轮只看是否稳定复现。

### 可能为空的预测

- **P6**：我**不**预期处理组代码质量更高。前四轮质量面一直打平，没理由变。
- **P7**：我**不**预期处理组更快。它多走流程，大概更慢。

## 判定方式

不采信任何一组的自述。我自己：
1. 把两组产出各自 checkout 到独立 worktree，跑 `go test ./...`；
2. 用我**在启动前写好、两组都看不到**的验收用例跑两组产出（见 `acceptance/`）；
3. `go vet`、`gofmt -l`、`go test -race` 各跑一遍；
4. 数单元数、计划行数、用例数，核对每条新用例在 0.2.0 上的实跑结果。
