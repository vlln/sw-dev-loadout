# 执行阶段也撞了预算墙（两次，两组同时）

第一次尝试（计划+实现同一个 agent）两组都在计划阶段耗尽预算。改成计划/执行两段之后，
**执行者又双双在实现中途耗尽**：

| | 基线 | 处理组 |
|---|---|---|
| 死掉时的提交数 | 0（单元 1 未提交） | 1（单元 1 已提交） |
| 工作树里的未提交内容 | `money.go` + `positive_test.go` | `store.go` + `transfer_test.go` |
| 死掉时测试状态 | 全绿 | 全绿 |

两组都死在第一或第二个单元上，而两份计划都写了 3~4 个单元。

## 这说明什么，不说明什么

**不说明**带不带 skill 有差别——两组同时死，死的位置几乎一样（处理组多一个提交，
因为它的单元 1 更小）。

**说明一件关于计划的事**：两份计划都把工作切成了"每个单元能独立编译、独立测试、独立回归"的形状，
于是中途断电时留下的是**一个可用的半成品**，不是一堆改到一半的文件。两组都是：测试全绿、
树能构建、下一个接手的人能从 `git log` 读出进度。

处理组多拿到一个提交，原因正是它的切法——单元 1 只改 `money`，更小，所以先落地了。
这是"切到能单独判断就够"这条规则在非预期场景下的一次副作用验证：**切片的价值不只在评审，
也在中断恢复。** 两份计划都没写这个理由，是实验撞出来的。

## 装置上的教训

一次对照里，单个 agent 的预算是个硬约束，它和夹具规模直接冲突。第四轮夹具 85 行，
一个 agent 从头走到尾绰绰有余；这轮 403 行 + 7 条需求，计划和实现各自都要一个完整预算。

下一轮要么继续按单元分段（每个单元一个执行者，交接靠 `git log` 和 `DEVIATIONS.md`），
要么把夹具控制在 200 行上下。**不能既要大夹具又要单 agent 跑完。**
