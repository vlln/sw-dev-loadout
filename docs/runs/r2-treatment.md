# tally 0.4.0 实施计划：`--json` 与 stdin

> 输入：`repo/FEATURE.md`（`--json`、`-` 读 stdin、二进制跳过、空输入/坏路径非零退出、现有 CLI 是公开接口）。
> 本文件只写计划，不含实现代码；除输出本文件与在 `/tmp` 下做行为探针外，未改动仓库。

## 0 结论、现状与冻结清单

### 0.1 一句话结论

这是一个约 15 行的 CLI，功能量很小，但它的**全部难点都在兼容性上**：`FEATURE.md` 明说已有用户脚本调用它，而当前实现里有多处"看起来像 bug、但已经是公开输出"的细节（行数约定、排序、扩展名派生、静默跳过）。计划的核心不是"怎么加 `--json`"，而是**先把现有字节级行为钉住，再在失败路径与新增开关上动刀，成功路径一个字节都不改**。

### 0.2 现状事实（本次实测，非推测）

环境：Node `v22.23.1`，`node --test` 1 条用例通过，`package.json` 版本 `0.3.0`，`bin` → `src/cli.mjs`。

| 事实 | 实测结果 |
|---|---|
| 表格行格式 | `<ext 左补空格到最宽 ext>` + 两个空格 + 行数 + `\n`（`od -c` 确认无尾随空格） |
| 行序 | 按行数**降序**；并列时保持首次出现顺序（`Map` 插入序 + 稳定排序） |
| 行数约定 | `split('\n').length`：以换行结尾的文件**多算 1 行**（`one\ntwo\n` → 3）；空文件 → 1 行 |
| 扩展名派生 | 取**整条路径字符串**最后一个 `.` 之后的子串：`dir.v1/f` → `.v1/f`，`./noext` → `./noext`，无点 → `(none)` |
| 二进制跳过 | 只看文件名后缀 `png/jpg/gif/zip/pdf`（大小写不敏感），静默跳过，不算错误 |
| 全部跳过 | stdout 0 字节，exit 0 |
| 无参数 | stderr `usage: tally <file...>`，exit 2 |
| 不存在的路径 | 未捕获 `ENOENT` 栈打到 stderr，exit 1，**stdout 0 字节** |
| 未知 flag | 被当成路径：`--json` → ENOENT、exit 1 |
| `-` | 被当成名为 `-` 的文件：ENOENT、exit 1 |
| 重复路径 | 重复计数（`a.ts a.ts` → 6） |
| 仓库状态 | **不是 git 仓库**（无 `.git`、无远端、无 CI、无 lint/coverage/CHANGELOG/LICENSE） |
| 环境噪声 | 本机 `NODE_USE_ENV_PROXY=1` 使**每个** node 进程向 stderr 打 `UNDICI-EHPA` 实验性警告 —— 任何 `stderr === ''` 断言必须先净化环境，否则假红 |

最后两条直接影响第 3、4 部分，单独记：仓库没有版本锚点与 CI，所有证据只有本地；`stderr` 断言在净化前不可信。

### 0.3 冻结清单（本次不得改变，逐条对应一条回归钉）

1. 表格行格式（含两个空格分隔与补齐规则）。
2. 按行数降序、并列按首次出现顺序。
3. 扩展名派生规则，**含上表那条已知缺陷**。
4. 无扩展名标签 `(none)`。
5. 行数约定 `split('\n').length`（含尾换行多算 1）。
6. 跳过仍只看后缀、静默、不算错误；全部跳过仍 exit 0。
7. 无参数仍 stderr usage + exit 2。
8. 重复路径仍重复计数。
9. 成功时 stdout 只有一个表格，无其他字节（**不得**加"已跳过 2 个二进制文件"之类的一行摘要），exit 0。

### 0.4 会改变的公开行为（全部在失败路径或新开关上，逐项写进 PR 披露）

| 变化 | 从 | 到 | 影响面 |
|---|---|---|---|
| 坏路径的 stderr | 未捕获栈 | 一行可读信息（路径 + 下一步） | 用 grep 抓栈或抓 `ENOENT` 的脚本 |
| 坏路径的报告量 | 第一个坏路径即中断 | 一次报告全部坏路径，仍 exit 1 | 只影响错误文本，不影响退出码 |
| 未知 flag | 当路径 → exit 1 | exit 2 + usage | 任何 `!= 0` 判断不受影响 |
| usage 文本 | `usage: tally <file...>` | 追加 `[--json]`、`-`、`--`、退出码提示 | 抓 stderr 文本的脚本 |
| 新行为 | — | `--json`、`-`、`--`、stdin | 纯新增 |
| 成功路径 | — | **不变** | — |

### 0.5 明确的范围外（本次不做，避免顺手扩面）

递归目录 / glob 展开、`--help`、`--quiet`、排序或过滤选项、总计与元数据字段、颜色、CHANGELOG、CI、lint、覆盖率门禁、`files` 字段与打包瘦身、包名与 `bin` 改名、stdin 的流式增量计数（与现状一致：全量读入内存）、修复 0.3 冻结清单第 3 条（扩展名派生缺陷）、修复行数约定的 off-by-one。

## 1 实施步骤

顺序的判据是"后一步需要前一步提供的结构或锚点"，不是"哪步最像功能"。每步给出完成信号，信号都是可观察的。

### 步骤 0 — 冻结基线（不改代码）

用一组固定 fixture 记录当前 CLI 的 stdout 字节、stderr、退出码：正常两文件、单文件、长扩展名（触发补齐）、空文件、全二进制、无参数、缺路径、缺路径+有效路径、未知 flag、重复路径、含点目录。

为什么在最前：后面每一步都要回答"哪些字节变了"。没有这张表，PR1 的"零行为变化"和 PR2 的"只动失败路径"都只是声明。

完成信号：基线表成型，字段包含命令、stdout 字节（`od -c` 级）、stderr 摘要、退出码。它的长期形态是 PR1 里的断言字面量，不引入生成物或快照机制（这个仓库没有生成器，加一套是过度工程）。

### 步骤 1 — 可测性重构（零行为变化）

把 `src/cli.mjs` 从"既是入口又是实现"拆成四块**无副作用**单元，`cli.mjs` 只剩薄入口：

- 参数解析（纯函数：argv → `{ json, paths, stdinRequested }` 或一个用法类错误）；
- 扩展名派生（**唯一一处**，供文件与 stdin 共用）；
- 渲染（表格渲染器 / JSON 渲染器，输入是同一份"按扩展名聚合后的有序行集合"）；
- 计数组合（`countFiles` 保持现有签名与语义，另外补一条只吃文本的入口供 stdin 用）。

`cli.mjs` 仍必须是 `bin` 指向的文件，只负责：取 `process.argv`、必要时读 stdin、调用上述单元、写 stdout/stderr、设置退出码。它需要变成 async（见步骤 3 的平台约束）。

为什么先做：步骤 2/3/4 都要动"参数从哪来、输出写到哪、退出码谁定"。不先定结构，三个 PR 会各重写一遍 `cli.mjs`，评审看到的是三份互不相关的入口。

不变式：`test/count.test.mjs` **一行不改**且仍绿（它的未被修改本身就是"计数语义没动"的证据）；扩展名派生保持原语义，包括缺陷。

完成信号：基线表逐字节重放一致（含 stderr 与退出码）；现有单测未修改通过；PR1 同时加入钉住 0.3 节全部 9 条的回归测试（它们在重构前后都必须通过）。

### 步骤 2 — 失败与退出码契约（本计划唯一的行为变化步）

- **两阶段**：先解析并校验（flag 合法性、路径存在性/可读性），再读取计数，最后才渲染。渲染前不往 stdout 写一个字节。
- 退出码分级：`0` 成功；`2` 用法类（无输入、未知 flag、重复 `-`）；`1` 输入/IO 类（不存在、不可读）。
- 失败消息：一行，含出问题的路径、违反的规则、下一步该做什么；一次报告全部坏路径；错误走 stderr，永远不混进 stdout。
- 保留现状里已经成立的保证（失败时 stdout 0 字节、exit 1），只是把"未捕获栈"换成可读文本。
- 状态保证：stdout 为**无效果**（失败后与调用前相同）；stderr 为**可部分**（可能只列出部分坏路径）；不写任何文件、不重试、无外部副作用。

为什么在 stdin 之前：stdin 的失败（重复 `-`、空 stdin）只是这套分级的新实例；先定分级，stdin 那步就只剩"多一个输入源"，不用二次发明错误语义。

完成信号：基线里"缺路径"那一条的栈消失、退出码仍为 1、stdout 仍 0 字节；未知 flag 从 1 变 2 并被 usage 覆盖。

### 步骤 3 — stdin（`-`）

- `-` 表示读 stdin；与文件路径可以混用，聚合进同一张表（同一个扩展名桶相加）。
- stdin 与文件共用同一个计数函数（因此 `printf 'a\nb\n' | tally -` 与"同样内容的文件"结果相同），共用同一个扩展名标签规则（标签取值见 D3）。
- **只读一次 stdin**；重复 `-` 报用法错误（D3）。
- **不给 `-` 时绝不读 stdin**：任何实现只要无条件抽干 stdin，`tally a.ts` 在管道或交互 shell 下就会挂住。这是本步唯一的高危点，单独一条验收与一条测试。
- stdin 一律按文本处理，不做内容嗅探（D10）；理由在文档里写明：跳过规则本来就是**基于文件名**的，stdin 没有文件名，所以"按文本"是从既有规则推出来的，不是随意双标。
- 平台约束：不要用按 fd 读的同步读取（如读 fd 0），那在非 POSIX 平台不可用；走 `process.stdin` 流式读入再拼接，因此入口需要 async。这属于实现细节，但它决定了步骤 1 的入口形态，所以写进计划。

完成信号：`printf 'a\nb\n' | tally -` 得到与文件一致的计数；`tally - <file>` 聚合成一行；`tally <file>` 在有未闭合 stdin 时仍立即返回。

### 步骤 4 — `--json`

- 与表格**共用同一份有序聚合结果**，只是第二个渲染器 —— 这是"两种输出永不错位"能被当作契约而不是巧合的原因。
- 位置无关（路径前或后都接受）；与无路径组合时沿用步骤 2 的用法类失败，**不**输出半成品 JSON。
- stdout 纯度：只有一个 JSON 文档 + 一个结尾换行，无 BOM、无前缀、无提示；`stderr` 不含 JSON。
- 形态：单个对象，键是扩展名（含点 / `(none)` / stdin 标签），值是整数行数；键序与表格一致（契约，见 D2）。不加 total、不加元数据、不加时间戳（未要求，且每加一个字段就是永久兼容负担）。
- 跳过与错误语义完全继承：跳过的文件不出现在 JSON 里；成功才输出，失败时 stdout 为空。

完成信号：`tally --json a.ts b.md` 可被 `JSON.parse`，且与 `tally a.ts b.md` 逐行一致；`--json` 无路径时 exit 2 且 stdout 为空。

### 步骤 5 — 文档与版本

- README 补成**消费者契约**：用法、`--json` 形态与一个示例、`-`、退出码表（0/1/2）、跳过规则、排序规则、行数约定（含尾换行那条，明确写成"按 `\n` 分隔计数，因此以换行结尾的文件多计一行"）、以及"stdin 按文本、标签为 `(none)`"。只写当前态，不写"新增""以前"。
- 每条示例命令都要亲手跑过，README 里的输出与真实输出一致。
- `package.json` 版本 `0.3.0` → `0.4.0`（D8）；`bin` 路径、`engines`、包名不动。
- 为什么和其他步分开：文档可以独立评审"读者能否只凭它写脚本"，且它把 D2/D3 的结论固化成文字。

完成信号：一个没读过代码的人能凭 README 写出 `tally --json … | jq` 并正确解释 1/2 退出码的区别。

### 步骤 6 — 整体验证与收口

跑第 3 部分全部检查（含负控与打包冒烟），把证据落进 PR 描述，残余缺口写进"未验证 + 谁接受"。

完成信号：每条验收条件都能指到一条跑过的证据；没有证据的条件被显式记为缺口，而不是被省略。

## 2 验收条件

每条都可观察，且在第 3 部分有对应证据。`A1`–`A4` 是兼容性与正确性，`A5`–`A9` 是新功能与失败语义，`A10`–`A12` 是文档与发布形态。

| # | 条件（怎样算做完） | 如何观察 |
|---|---|---|

| A2 | `tally --json <files>` 在 stdout 输出**恰好一个** JSON 文档 + 一个换行；`JSON.parse` 成功；键是扩展名标签（带点 / `(none)` / stdin 标签，随输入而定）、值是整数行数；stderr 为空；exit 0 | 解析 + 字节断言；`stderr === ''` 需在净化环境后成立 |
| A3 | 同一份输入下，JSON 与表格**逐行一致**：集合相同、顺序相同、数值相同 | 一次解析两侧再比对（不是分别断言两组字面量） |

| A5 | `printf 'a\nb\n' \| tally -` → exit 0，计 3 行，归入约定的无扩展名标签；`tally - <file>` 聚合成一行（同扩展名相加） | stdin 用例 + 混合用例 |
| A6 | 不给 `-` 时**不读 stdin**：stdin 是未闭合的管道时，`tally <file>` 仍立即结束并 exit 0 | 子进程不关闭 stdin，等退出信号并设上界（详见 3.3） |
| A7 | 不存在的路径（单独或与有效路径混用）→ exit 1、stdout **0 字节**、stderr 含该路径与下一步提示；一次运行报告全部坏路径 | 断言退出码 + stdout 字节数 + stderr 子串 |
| A8 | 空 stdin（`-` 且 0 字节）→ 非零（约定为 1）+ 可读消息、stdout 0 字节 | 空输入用例（语义见 D1） |
| A9 | 用法类错误统一 exit 2 + usage：无参数（现状）、未知 flag、重复 `-`；未知 flag 不再被当路径 | 三条用例 |
| A10 | 二进制后缀文件不出现在表格与 JSON 里，且不算错误；全部输入都被跳过时 exit 0（表格模式 stdout 空、JSON 模式 `{}`） | 两个模式各一条 |
| A11 | README 覆盖：用法、`--json` 形态、`-`、退出码 0/1/2、跳过规则、排序规则、行数约定、stdin 标签与"按文本"；文中每条示例命令的输出与实际一致 | 人工逐条执行示例；由评审者核（无机械门禁，见 3.5） |
| A12 | `npm pack` 产物包含入口实际引用的全部模块；解包后直接运行 `--json` 与 `-` 两种用法都正常，不依赖仓库内相对路径 | 打包 → 解包 → 在临时目录跑一次 |

补充两条断言纪律（属于验收，不属于偏好）："断言没有发生"的用例必须同时断言一件本该发生的事（例如 A7 断言 stdout 为空时，同一用例里另有一条断言 exit 1 与 stderr 有内容，避免组件根本没启动也通过）；失败后的状态断言只看外部可见面（退出码 / 字节 / 文本），不看内部函数是否被调用。

## 3 验证计划

### 3.1 表面 → 证据（先定表面，再定证据）

| 触达的表面 | 谁观察 | 最窄证据 | 为什么它够 |
|---|---|---|---|
| 模块级计数（`count.mjs`） | 进程内调用者 | 现有 `test/count.test.mjs`（**保持不改**） | 它就是该模块唯一的契约测试；不改它本身就是"语义没动"的证据 |
| CLI 的 stdout / stderr / 退出码 | 用户、脚本、CI | 新增黑盒用例：`spawnSync(process.execPath, [cli, …])` 捕获三通道 | 公开接口是**进程**，不是被重导出函数。替身组合证明不了退出码与字节 |

| T15 | 缺路径 + 有效路径 | 同上，且两条坏路径都出现在 stderr | A7 | **失败**（只报第一个 + 栈） |
| T16 | `tally <file>` 且 stdin 是不关闭的管道 | 进程仍退出、exit 0 | A6 | 通过（回归钉；实现错误才会红） |
| T17 | 空 stdin（0 字节） | exit 1、stdout 0 字节、可读消息 | A8 | **失败**（文案是 ENOENT 栈） |
| T18 | 未知 flag `--jsn` | exit 2 + usage，stdout 0 字节 | A9 | **失败**（exit 1） |
| T19 | 重复 `-` | exit 2 + usage | A9 | **失败** |
| T20 | `--` 终止符 + 形似 flag 的文件名 | 正常计数 | A9 | **失败**（视为 flag/路径） |
| T21 | 不可读文件（chmod 000） | exit 1 + 可读消息 | A7 | **失败**（栈）；以 root 运行时该用例显式跳过并注明原因 |

T1–T6 与 T16 是**回归钉**：它们现在就通过，作用是让"没改"可被验证，而不是新证据。T7–T15、T17–T21 是**新证据**：它们在 0.3.0 上必须失败（例外：T14 现状只满足一半 —— 退出码与空 stdout 已成立，文案是栈），失败原因必须是"功能缺失"而不是"测试写错"（见 3.4）。

关于"跑全套"：`change-evidence` 反对的是"不知道跑什么所以默认跑全套"。这里全套约 21 条、每条一次 `spawnSync`（合计 1–2 秒），**这套测试就是最窄证据本身**，不是更广检查的替代品，且仓库没有 CI，本地这一次就是全部证据。因此"本地跑全套 cli 测试 + 单跑 count 单测"不构成过度。

### 3.3 确定性与环境纪律

- **净化子进程环境**：删除 `NODE_USE_ENV_PROXY`（本机实测它让每个 node 进程往 stderr 打 `UNDICI-EHPA` 警告），并删除 `NODE_OPTIONS`。不这么做，T7/T13 的 `stderr === ''` 会假红，且本机与 CI 结论不一致。
  - 为什么不用 `--no-warnings`：那会连带吞掉 tally 自己可能发出的警告，把噪音变成不可见而不是消除。净化环境恢复的是"被测进程的默认条件"，方向是对的。
- 资源分配：临时目录走内建 `mkdtempSync`；文件用绝对路径，或把子进程 `cwd` 设在临时目录，避免与仓库内同名文件互相干扰。
- **等完成信号，不等时间**：不用 sleep 做同步。唯一的时间上界是 T16（不读 stdin）：等子进程退出、超时只作上界（数秒），断言的是退出码而不是耗时。
- 不依赖 TTY：测试永远显式提供 stdin；TTY 分支的行为按 D7 记录为决策，不做断言（无自动化手段，见 3.6）。
- 断言外部状态：退出码、stdout 字节、stderr 文本；不断言内部函数被调用（PR1 之后的单元测试除外）。
- 平台语义：读取 stdin 走流而非按 fd 同步读，避开非 POSIX 平台的 fd 0 问题；路径拼接用内建 path 模块，不手拼分隔符。
- 不做的"修复"：不因某个断言难写而放宽断言、不加大重试、不把输出归一化掉。

### 3.4 先证明它真的会失败

实现之前，在 **0.3.0 代码**上跑一遍新测试，逐条记录失败表现，期望与 3.2 最后一列一致：

- T7/T8/T9/T13 → `--json` 被当路径，ENOENT/exit 1；
- T10/T18/T19 → exit 1 而非 2；
- T11/T12 → 名为 `-` 的文件不存在；
- T14 → 仍为 exit 1、stdout 仍 0 字节，但 stderr 是未捕获栈（这条不算失败，只验证"已成立的保证别退化"）；
- T15/T17/T21 → 未捕获异常的栈；
- T20 → 形似 flag 的文件名被当成 flag。

任何一条**通过**了，说明测试没有测到它声称的行为，必须先改测试。这一步是"证据可能失败"的证明，也是把"我加的功能真的被覆盖了"从声明变成观察的唯一手段。

### 3.5 明确不跑的检查，以及理由

| 不跑 | 理由 | 缺口如何处理 |

| 覆盖率门禁 | 仓库没有；引入它属于工程标准采纳（`engineering-standards` 的 L2 档），是独立决定，不夹进本 PR | 记为范围外 |

## 4 落地安排

### 4.1 硬前置：这个目录不是 git 仓库

`repo/` 没有 `.git`、没有远端、没有 CI、没有标签。这不是形式问题：**没有版本锚点，"回退"与"当前已发布版本"都无从谈起**，而第 4.4 节的回退安排整个依赖它。

两种可能，需要人确认（D9）：

- 这是真仓库的分发副本 → 先在真实仓库里核对主干、当前版本（`0.3.0`）与实际已发布版本是否一致，再把本计划的 PR 切片映射过去。
- 这就是源仓库 → 先做一次性的仓库初始化（默认分支、`.gitignore`、远端、向主干打一个 `v0.3.0` 基线提交/标签），然后才开始 PR1。

在这一点澄清前，计划可以按下面的切片准备，但**不应开始合入**。

### 4.2 PR 切片与依赖顺序

每个 PR 恰好一种性质。四个 PR 的顺序是依赖顺序（都碰 `cli.mjs` 及其相邻模块），不是偏好顺序。

| PR | 性质 | 范围 | 风险 | 依赖 |
|---|---|---|---|---|
| PR1 | 重构（含冻结现状的回归钉测试） | 拆四个无副作用单元 + 薄入口；**无行为变化** | 低 | 主干（含 0.3.0 基线锚点） |
| PR2 | 行为修复（失败路径） | 两阶段校验、退出码分级、可读错误、报告全部坏路径、未知 flag → 2 | 中 | PR1 |
| PR3 | 新功能 | `-` 读 stdin、聚合、只读一次、不读 stdin 的保证 | 中低 | PR2 |
| PR4 | 新功能 + 文档 | `--json` 渲染器、README 契约、版本 0.4.0 | 中 | PR3 |

- 依赖链用平台**官方**的 stacked PR 机制（每层自己的描述只覆盖相对自己基线的这一层）。
- 官方栈不可用或跨 fork 时**不手工改 base 复刻栈语义**：改成顺序合入（PR1 合入 → 再开 PR2，以此类推）。顺序合入不是手搓栈，是放弃并行。
- 可选的合并（需评审者同意）：**把 PR1 并入 PR2**。代价要说清：评审者要同时判断"结构变了"和"失败路径变了"，而 PR1 的价值恰恰是"字节级无变化"这条证据单独成立、单独可读。**不建议**合并 PR3 与 PR4（两个功能彼此独立，各自的失败模式不同）。
- 切片纪律：每个 PR 只碰自己范围内的文件；0.5 节的任何一项都不许夹带；发现无关问题另开 PR 或在记录里写下。

### 4.3 风险分级与审批路由

判级依据是实际 diff、暴露面与可逆性，不是行数。

| PR | 为什么是这个等级 | 需要的批准 | 回退 |
|---|---|---|---|
| PR1 | 不改变任何外部可观察行为（字节级证据）；纯内部结构 | 一名评审者核"无变化"。当前仓库**没有自主集成授权**（无 CI、无门禁、无政策文件），所以不适用"低风险免人类批准"——仍需人合入 | revert，无副作用 |
| PR2 | **唯一改变既有公开行为**的 PR：stderr 文案、报告条数、未知 flag 退出码 1→2。成功路径字节不变，所以爆炸半径限于失败路径，但"已有用户脚本"这句使兼容性判断必须由人做 | 一名有权者 + 一名"脚本消费者代表"的兼容 sign-off（确认改 stderr 文本可接受）。两个角色可由同一人兼任，但结论要分开写 | revert，无数据影响 |
| PR3 | 纯新增输入通道；高危点是"不给 `-` 时误读 stdin"，可由 T16 拦住 | 一名评审者 | revert |
| PR4 | 新增**永久兼容面**：JSON 形态与键序一旦发布就难改；同时引入版本号变更 | 一名评审者 + 版本/发布 owner 对 0.4.0 与 JSON 契约点头（D2/D8） | revert（已发布版本号不可回收，需发 0.4.1） |

三点纪律：

- 判级由非作者给出，并另有一个独立上下文回答"即使判为中风险，是否仍需升级"——敏感面（发布、安装/发行通道）在本项目里确实存在，不能靠"改动在文档或新开关里"绕开。
- **合并 ≠ 发布 ≠ 打标签**，三个动作各自授权。`npm publish` 与 `v0.4.0` 标签是独立动作，需要针对该动作的明确批准，不因"PR4 已合入"自动成立。
- 前面任何批准都不覆盖后续新提交：PR4 合并前若 base 前进，做差额复审而不是重演整套审批。

### 4.4 发布、观察与回退

- 发布前对**已合并候选**重跑一次：README 全部示例 + `npm pack` 冒烟（不能复用 PR 分支上的证据）。
- 观察面：这个项目没有遥测。可观察的是发布后关于"退出码变了/错误文案变了"的反馈，以及 README 示例在真实安装下的表现。合入者/发布者在发布后 48 小时内持有这份观察责任，并指定交接人（不能因会话结束留下无人负责）。
- 回退：revert + 发布 `0.4.1`。为什么回退是安全的：成功路径的 stdout 契约没变，回退只影响新开关与失败文案；唯一不可逆的是已经发出去的版本号本身。
- 不做的事：不打乱历史重写；不用裸强推；若确需重写只用带期望 OID 的 `--force-with-lease`。

### 4.5 PR 描述要点（四栏，写"为什么"）

- **动机**：一句话——脚本需要机器可读输出、管道需要从 stdin 取数；引 `FEATURE.md` 对应条目，并把"现有 CLI 是公开接口、已有脚本调用它"写进动机（它决定了本 PR 的取舍）。
- **变更**：分栏。
  - 接口变化：新 flag `--json`、新路径 `-`、`--`、退出码分级（0/1/2）、stderr 文案、JSON 文档形态。
  - 行为变化：**成功路径无**（PR1/PR3/PR4 的成功输出要么不变，要么是新增模式）；PR2 只有失败路径变化，逐条列 0.4 节那张表。
- **测试**：先设计后条目。PR1 走"无行为改变的迁移"形式（字节对照 + 未变的断言）；PR2 走"行为改变"形式（场景 × 改前 × 改后 × 覆盖用例）；PR4 同样走行为改变。每条只列**跑过**的命令与结果，标注本地；未跑的（Node 20、Windows、TTY）单列，不混入"通过"。
- **披露**：逐项——改了 usage 文案、改了未知 flag 退出码、改了失败文案与报告条数、JSON 键序被定为契约、Node 20/非 POSIX 未验证的豁免及接受人。证据放可折叠块，长输出只留命令、计数与结论。
