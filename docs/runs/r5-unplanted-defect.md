# 夹具里一处我没埋的真缺陷（两组都自己找到了）

`money.Parse` 静默溢出，`err == nil`。我独立实跑确认（`/tmp/ovf2`，0.2.0 源码）：

| 输入 | 解析结果 | `String()` | err |
|---|---|---|---|
| `184467440737095516.20` | 4 | `0.04` | nil |
| `9223372036854775807` | -100 | `-1.00` | nil |
| `184467440737095517` | 84 | `0.84` | nil |
| `92233720368547758.08` | -9223372036854775808 | 负的最大值 | nil |
| `92233720368547758.07` | 9223372036854775807 | 真正的 MaxInt64，合法 | nil |

原因是 `total := w*100 + f` 没做范围检查，`strconv.ParseInt` 只保证 `w` 本身不溢出。

## 为什么要紧

它不是美观问题，而是**绕过 R2 与 R7**：

- R2 要求金额严格大于 0。一个 18 位的请求解析成 4 分，`amt > 0` 检查通过，转账照做。
- R7 的透支算术在溢出后的值上做，下限形同虚设。

也就是说，只在 api 层写 `amt <= 0` 的实现**不满足 R2**，尽管它看起来满足。

## 这条要怎么计入结论

**不计入 skill 的功劳。** 两组都找到了它，都做了实测，都把修补隔离在 `internal/money` 单元里
（理由一致：这是唯一改到现有函数体的改动，和它一起的现有测试需要能单独回归）。
基线甚至指出 `TestParseRejectsOverflow` 是它新增用例里**唯一一条在 0.2.0 上能编译且失败**的，
其余都是"因为路由不存在"或"因为不编译"而失败——那种失败只证明东西还没写。

它说明的是夹具的另一件事：**我以为我知道夹具里有什么，其实不知道。** 造夹具时我验了自己埋的
两处，没有去问"还有别的吗"。下一轮造夹具要多一步：对被改动的函数做一次边界扫描，
把发现的缺陷**写进夹具文档**——否则它会在对照里变成噪声，两组谁先撞上谁就显得更强。
