# 第五轮：大夹具复验「流程深度与改动规模成比例」

夹具 `ledger` 0.2.0（Go HTTP 服务，403 行代码 / 267 行测试 / 17 用例 / 3 个包），需求 7 条加一个转账端点。预测在动手前写下（[r5-predictions.md](r5-predictions.md)），结果出来后未改动。

这份夹具是为上一轮验不出的那条规则造的：规模是第四轮的 4.7 倍，且 7 条需求看着像 7 个单元、实际上 R1/R6/R7 共用同一段临界区——按需求条数拆必然返工。两处埋点（锁不可重入、错误信封缺 409）在 0.2.0 上实测确认过。另配一套启动前冻结的黑盒验收探针（41 条，在 0.2.0 上只有 3 条旧行为守卫通过）。

## 装置先失败了一次，然后是第二次

- **第一次尝试**：计划+实现同一个 agent 从头走到尾。两组都在预算耗尽时中止，零提交。死因不同（基线是任务对单次预算太大，处理组是读 1,900 行 skill 吃掉了预算），不计入对照。详见 [r5-aborted-attempt.md](r5-aborted-attempt.md)。基线中止时留下的 149 行部分计划**在无 skill 的情况下自己识别了两处埋点**——这个夹具的埋点，认真的基线找得到。
- **改成两段**：两组各自只写计划，再各派一个执行者照做（和第二、三轮同形）。
- **第二次失败**：两个执行者又双双在实现中途耗尽预算。详见 [r5-exec-budget.md](r5-exec-budget.md)。半成品都已提交、测试全绿、bundle 可恢复（基线 20 用例、处理组 32 用例全绿），验收探针在两组上都只过 3/41——端点没接完，判不出差别。

所以**本轮的主证据是计划阶段**，执行阶段只贡献了一条意外观察：两份计划切出的单元都是"可独立编译、独立测试"的形状，中途断电留下的是能直接接手的半成品，不是改到一半的废墟。切片的价值不只在评审，也在中断恢复——两份计划都没写这个理由，是撞出来的。

## 逐条核对预测

- **P1（基线按需求条数拆 ≥5 个单元；处理组 ≤3 且给出耦合理由）：预测错了。** 基线切了 4 个单元，依据是编译依赖与耦合，并且显式写下"7 个不行：R1/R2/R4/R6/R7 落在同一个 `Transfer` 函数体里，无法独立落地或回退"。处理组切 3 个，理由同构。这轮规则的差分信号根本没有出现。
- **P2（这次改动不小，处理组不会明显更短）：方向成立但预测写得弱。** 723 > 491。多出来的不是切碎，是风险相应的过程产物：AST 口径门禁（带自证测试）、两份决策记录、评审路由、一页"刻意不加的测试"及理由。
- **P3（至少一组撞上死锁或留下第二个余额口径）：没触发。** 两组都在计划阶段点名这个坑并用同一个办法绕开。处理组的半成品 Unit 2 已核验：一次加锁、`balanceOf`、`-race` 干净。
- **P4（至少一组交出的 409 实际是 500）：没触发。** 两组都在计划阶段发现映射表缺 `overdraft` 键。
- **P5（处理组逐条预判旧版本结果且与实跑一致）：处理组做了，但基线这轮也做了。** 基线的 §4 同样逐条给出 0.2.0 判定并实测了溢出值。规则 B 的差分在这轮消失——不因此降级（它已有两个夹具的确认），但要记下：这套 set 能赢基线的窗口在缩小。
- **P6（质量面无差别）：成立。** 两组都找到了我没埋的 Parse 溢出，修复在边界上逐字节等价（`92233720368547758.07` 放行、`.08` 拒绝，我独立实跑确认）。
- **P7（处理组更慢）：测不出。** 计划阶段处理组反而先交（它先读完 skill 再动笔，基线在 `/tmp` 里做了更多原型验证）；执行阶段两组都中止。

## 一处两组都没放过的需求矛盾，和一处只有处理组升级的歧义

- **R5×R6 矛盾**（重放返回"首次的结果" vs 余额口径唯一）：基线发现、实测了两种实现、选了 R6 并写明"这是计划里唯一一处有意不按字面读需求"。处理组的等价位置只在 P2 附近间接触及。**我冻结的验收探针判不了这处**（首次与重放之间没有改动余额，两种实现都过），见 [r5-probe-limits.md](r5-probe-limits.md)。
- **R5 同键不同体**：处理组把它标成"需要人决定"，拒绝写测试去祝福字面读法（"pinning it would make a disputed reading look settled"），给出后续 409 方案。基线自己拍了板（不检测、记录局限）。这正是 `review-gate` 第四轮补的那条规则想要的行为差别，但基线的处理同样站得住——记为弱支持，只有一个实例，不升级。

## 一处我没埋的真缺陷

`money.Parse` 静默溢出：`184467440737095516.20` 解析成 0.04 且 `err == nil`，只在 api 层写 `amt > 0` 的实现其实不满足 R2。**两组都自己找到了它**，都做了实测，都把它隔离进 `internal/money` 单元。不计入 skill 的功劳；详见 [r5-unplanted-defect.md](r5-unplanted-defect.md)。教训已写进 `improvement-loop`：造夹具时对被改动的函数做边界扫描，没埋的缺陷要写进夹具文档。

## 规则分级变动

- **规则 A（流程深度与改动规模成比例）：仍是候选，但证据结构变了。** 这轮终于给了它失败的机会——夹具大到有拆分诱惑——而预言的失败形态没有出现：基线一样按耦合切。同时第二轮的真实缺陷形态（处理组把 63 行改动拆成 4 个 PR）没有复发：处理组切得比基线还少（3 vs 4），深度花在了风险相应的地方。也就是说：规则针对的病在第二个夹具上没复发，但这不构成对基线的差分胜利。
- **规则 B（新证据必须在改动前的版本上真跑一遍）：维持确认。** 这轮基线也做了，差分消失；规则本身的确认不依赖这一轮的差分。
- **「先判要求本身是否可满足」（review-gate，第四轮补）：弱支持一次。** 处理组把一条歧义需求升级给人，基线自行拍板。都是合格工程行为，差别在"谁有权拍板"。

## 这一轮能说什么

- 这套 set 在五轮里抓到的差分（第三轮、第四轮）都来自"基线没做而 skill 要求做"的纪律项；这轮基线把同样的纪律自己做到了。要么是这个夹具类上基线能力足够，要么是模型在漂移——无论哪种，**继续用"基线会犯、skill 会拦"的预测结构去验这套 set，分辨力会越来越差**。
- 执行阶段两次预算失败是装置教训：单个 agent 的预算和夹具规模直接冲突，下一轮要么按单元分段交接，要么把夹具控制在 200 行上下。已写进 `improvement-loop`。
- 仍然：每组每阶段只跑一次；出题、答题、判题是同一个模型；执行阶段不完整，验收探针没跑出有区分度的结果。
