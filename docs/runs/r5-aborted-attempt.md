# 第五轮第一次尝试：两组都没跑完（2026-11-01）

## 怎么设计的

和第四轮同形：一个 agent 从头走到尾——读需求 → 写 `PLAN.md` 并提交 → 实现 → 测试 → 写 `REPORT.md`。
两组唯一差别是处理组要先读 7 份 skill（约 1,900 行）。

## 发生了什么

两组都在预算耗尽时中止，一个提交都没产生。

- 基线组：写到 `PLAN.md` 第 149 行时中止，计划本身没写完，代码一行没动。
- 处理组：读完 7 份 skill 后就没有余量了，`PLAN.md` 是空的。

## 为什么这不是一个结果

两组的失败原因不同：基线组是"任务本身对单次预算太大"，处理组是"读 skill 吃掉了预算"。
后者是实验装置的缺陷，不是 skill 的性质——真实使用时 skill 由宿主按需加载，不占执行者的额度。
拿它当"带 skill 更慢"的证据是错的。

更要紧的是：**这轮要验的是拆分依据，而拆分依据写在计划里。** 让同一个 agent 既写计划又实现，
计划阶段的预算就和实现阶段抢额度，规模越大抢得越凶。第四轮夹具小，没暴露这个问题。

## 改成什么

拆成两段，和第二、三轮同形：

1. 两组各自只写计划（不写代码），产出写到仓库外的 `plans/`；
2. 另一个执行者拿到计划照做，两份计划的执行者互不可见、也不知道哪份带 skill。

这样计划的体量与拆分依据可以直接比，而"计划交给别人照做时撞上多少矛盾与返工"也量得出来——
正是 `improvement-loop` 要求的下游执行度量。

## 保留的东西

[baseline-partial-PLAN.md](baseline-partial-PLAN.md) 是中止时基线组写到的 149 行。
它**不计入本轮对照**（没写完，且重跑时是新 agent），只作为一条独立观察保留：

这份未完成的计划在没有任何 skill 的情况下，自己识别出了两处埋点——
决策 3 写明"`Transfer` 不能调用 `Balance`（会自死锁），若复制一份求和逻辑就出现了第二个口径"，
决策 8 写明要给状态码映射表加 `"overdraft": http.StatusConflict`。
它也没有按需求条数拆，而是切了 5 个单元（计划 / store / api / 文档 / 报告），理由是
"store 是不变量持有者，先把它测透，api 只剩映射，缺陷定位范围小"。

也就是说：**这个夹具的埋点，一个认真的基线是会自己发现的。** 这一点要写进结论，
否则会把"基线也能做对的事"记成 skill 的功劳。
