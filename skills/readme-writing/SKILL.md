# 写一份读者优先的 README

README 是给陌生人的落地页，不是给实现者的汇报材料。总判据一条：**先服务读者，后服务实现者**；下面每条判据都是它的展开。

## 事实：宿主怎么渲染

来源：GitHub Docs《About READMEs》《Collapsed sections》《Attaching files》、`github/markup`、shields.io。核对 **2026-10-31**，宿主或服务变更后重核。

- GitHub 从 `.github/`、仓库根、`docs/` 三处识别 README；并存时按 `.github/` → 根 → `docs/` 取一个。
- 渲染时**超过 500 KiB 的内容被截断**。
- 渲染页按标题自动生成 Outline 目录（页面右上角的图标），短 README 不必手写 TOC。
- `<details>` + `<summary>` 可用，`open` 让某一节默认展开；折叠区内的 Markdown 照常渲染。
- HTML 会被清洗：`script`、inline style、`class` / `id` 属性都被移除；图片经 CDN 缓存后再出图。
- 图片附件单张上限 10 MB；视频上传免费计划 10 MB、付费 100 MB，编码按浏览器，官方推荐 H.264。
- `gh` 的 `issue` 与 `pr` 的 `create`、`comment`、`edit` 支持 `--attach <文件>#<alt>` 上传图片或视频：正文里对本地文件的引用会被改写成上传后的 `user-attachments` URL。视频渲染为播放器，没有 alt 文本（核对 gh 2.102.0，2026-11-01；用前先 `gh issue create --help` 确认本机版本有这个选项）。
- shields.io 同时提供动态徽章与静态徽章，也可自托管。
- 代码块标注语言后才按该语言高亮（高亮由 `github/linguist` 提供）。
- 深浅色双 logo 的通行写法是 `<picture>` + `media="(prefers-color-scheme: …)"`（uv、sindresorhus/awesome 的 README 源码如此，2026-10-31 读）。

## 读者分层：一节只服务一类人

| 读者 | 带着什么问题来 | 在哪一屏 | 愿意给的时间 |
|---|---|---|---|
| 第一次来的人 | 这是什么、为谁做、凭什么用它 | 首屏 | 5 秒 |
| 想安装的人 | 哪条命令能装成 | 第二屏 | 30 秒 |
| 想找 API 的人 | 这个函数、参数、配置项怎么用 | 深处，多数情况该链接走 | 翻到即走 |
| 想贡献的人 | 本地怎么跑起来、规矩是什么 | 尾部，或 `CONTRIBUTING` | 愿意深读 |
| 只想知道改了什么的人 | 这一版变了什么 | 不在 README 里 | — |

判据：每个章节都要能指名它服务上表哪一行、落在哪一屏；指不出来或落在"深处"的，删掉或链接走。一节里混进第二类读者的内容，拆出去或链接出去。

## 信息层级：按读者做决定的顺序排

**首屏**（不滚动可见）：项目名、一句话定位（≤120 字符）、可选 1–3 枚徽章、有界面或可见输出时一张演示。首屏只回答"这是什么"。

构图随产品分：**命令驱动的工具**裸排（标题与正文都左对齐，原生 Markdown）；**展示驱动的产品**（价值要靠看来判断的）用海报式居中构图——hero 图、居中标题、居中定位句、一行精选导航、一排徽章，写法见 cookbook。居中的海报本身就是"这东西被认真对待过"的证据。

**第二屏**：安装或快速开始。一条可复制的最小命令，加跑通后的样子。

**中段**：用法、配置、功能清单。一条功能一行，详情链接到文档站或 `docs/`。

**尾部**：文档入口、贡献、致谢、许可。许可永远在最后。

顺序判据：章节顺序照**读者做决定的顺序**，不照**代码的模块顺序**。`src/` 下五个目录，不需要对应五节。

**体量判据跟决策链走，不按读者身份分。** README 统一服务同一个角色：正在决定要不要用它的用户（开发者要深入时会被链接引导走，深度永远住在链接后面）。每一节都要能回答"它在决策链上回答哪个问题"。决策链短的产品（库、CLI：是什么 → 装 → 跑通）自然落在 ≤150 行、`##` ≤8——这是对短链的观察，不是上限。决策链长的产品（有可见输出、有价格与信任面：好看 → 可信 → 多少钱 → 敢不敢装）一个功能一节一图是主内容不是装饰，行数随功能数涨（观察样本 269 行、12 节，核对 2026-11-01）；信任节（多少钱、数据在哪、怎么卸载、作者是谁）是决策输入，不算冗余。链短却超出上限时按下面顺序处理：

1. 完整命令表、字段表、`ctx` 之类的 API 清单 → 搬进 `docs/` 或生成的文档站，README 只留一条跑通路径加链接。
2. 一段"它是怎么工作的"如果超过半屏 → 缩成三句定位，细节进 `ARCHITECTURE.md`。
3. 每个保留的 `##` 都要能回答"读者不做这一步会怎样"；答不出的合并或删掉。

超过 150 行必须有理由，且理由是**读者需要**，不是"内容重要"。

搬走的内容必须在 README 里留一处链接（`docs/`、`howto/`、生成的文档站都行）；**没有去处，说明那份文档该补上，而不是可以不写**。

首屏内容按项目类型换，判据不换（先回答"这是什么"）：

| 类型 | 首屏给什么 | 观察样本（2026-10-31） |
|---|---|---|
| 库 / CLI | 定位句、版本徽章、一条最小安装命令 | uv |
| 有界面的应用 | 展示驱动：首屏一张截图或 GIF（或海报式构图），功能各一节一图，安装退到第二屏 | awesome-readme 收录的 GUI 项目多以 GIF 开场；dsh-media-desk（核对 2026-11-01） |
| 清单 / awesome 列表 | 一句话、目录；不需要安装节 | sindresorhus/awesome |
| 规范 / 纯文档仓库 | 一句话、分节导览；安装节可省 | anthropics/skills |

**不该进 README 的**，搬走而不是删掉：

| 内容 | 去处 |
|---|---|
| 实现细节、架构取舍、设计理由 | `ARCHITECTURE.md` 或 `docs/` |
| 逐文件说明（`src/foo.ts`：工具函数） | 代码与行内注释 |
| 开发过程、调试弯路、一次性实验 | 提交信息、issue、博客 |
| 测试报告、覆盖率数字、手抄的构建结果 | CI 徽章或 CI 报告链接 |
| 变更流水、版本历史 | `CHANGELOG.md` |
| 完整 API 参考、全部参数 | `API.md` 或生成的文档站 |

一句话检验：**删掉它，目标读者会不会看不懂？** 会，留下；只有改代码的人才需要，搬走。

## 视觉层：装饰服务于理解

**徽章** 1–3 枚，上限 5 枚。每枚回答一个真问题：能不能装（版本）、还维护吗（最近提交 / 发布）、许可、构建过没过。

- 一枚一个信息，不放同义徽章（两个版本号）。
- 不放自己不会看的徽章，也不用无信息的装饰徽章。
- 每枚都有 `alt`，并链到能验证它的页面。
- 静态徽章可本地托管，省掉每次渲染的外部请求。
- 一排到底就是徽章墙：读者会跳过整排，连同有用的那枚。
- 社会证明（star 数、许可）也是合法的真问题，放不放看读者做决策时用不用得上。多于 3 枚时，style 与色系必须全文统一——混排的一排在读者眼里是业余信号。

**logo 与 banner** 放顶部，居中或与标题同行，宽 200–500 px。有深浅色两版就都给。必须有 `alt`；没有 logo 时，一张真实截图胜过占位图。

**截图、GIF、视频** 位置紧贴它能说明的那段文字，演示放首屏，功能各配一张。

- 单张图 ≤5 MB，GIF ≤10 s、宽约 800 px；更大的素材外链，不塞进仓库。
- 视频不提交进代码分支——二进制进了历史，之后每次克隆都为它付费。用 `gh --attach` 上传为 GitHub 附件再嵌入，做法见 cookbook；要求媒体可重建、可审计时，改用仓库内的孤儿 assets 分支。
- 每张图配一句"它展示了什么"，不写"效果图""截图"。
- 界面截图要能看清控件；不放大、不糊图充数。

**一致性与节奏** 读者不会逐项检查视觉，但整体不统一会被感觉到：徽章同 style 同色系、展示图同宽度、深浅色成对、节间一个 `<br>`、图文单元左右交替。单看每条都可有可无，合起来是"作者在意细节"的信号——对展示驱动的产品，这个信号本身就是内容。

**表格** 用于并列比较：功能矩阵、平台支持、安装方式对照。不用表格做纯文字排版（多列文字、居中标题）；唯一的排版表例外是「截图 + 说明」的功能展示单元——宿主清洗 class 与 style 之后，图文并列只剩 `<table>` 这一种手段，写法见 cookbook。超过 5 列拆成两段。

**折叠区** 放少数人才要的细节：多平台安装脚本、完整参数表、FAQ 附录、长日志。首屏信息、安装主路径、许可不得折起来。

**排版**

- `#` 只有一个，章节从 `##` 起，子节 `###`，不跳级。
- 一节一个主题；段落之间、列表前后各留一个空行。
- 代码块一律标语言（`bash`、`console`、`python`、`json`）；命令与输出分块，输出用 `console`。
- 行内代码只包命令、路径、标识符，不包整句。
- 链接文字写目的地（"安装文档"），不写"这里"、"详情"。
- 图片与链接用仓库内相对路径（`docs/demo.gif`），不用本机绝对路径。
- `##` 章节超过 5 个时给手写 TOC，或依赖宿主的自动 Outline；手写就必须与标题逐条一致。
- 标点风格整篇统一；中英文之间留一个空格。

## 反模式：真实失败形态与修法

| 形态 | 为什么坏 | 修法 |
|---|---|---|
| 首屏是架构说明（"采用三层架构，位于 `src/core/`"） | 读者还不知道它是什么 | 首屏换定位句加演示，架构搬进 `ARCHITECTURE.md` |
| 逐文件说明占一整节 | 没人按目录树理解项目 | 删，只留"从哪个文件开始读" |
| 开发流水账（"最初……后来改成……"） | 只对作者有意义，且会过期 | 搬进 issue 或博客，README 只留结论 |
| 徽章墙：十几枚 CI、覆盖率、下载、星标 | 噪声淹没信号 | 留 1–3 枚回答真问题的 |
| 手写覆盖率与测试数字 | 下一次提交就失真 | 换 CI 徽章，或链接 CI 报告 |
| 装饰压过内容：三屏 GIF 后才有一句说明 | 首屏没有信息 | 把定位句提到视觉之前，或把视觉压进首屏 |
| 只有安装、没有"它是什么" | 读者无法判断该不该装 | 补一句话定位与目标读者 |
| 安装块不可复制：`<your-token>`、`...`、多版本混排 | 复制粘贴即失败 | 每个平台一个独立代码块，占位符写进注释 |
| CHANGELOG 粘进 README | 两处维护，必然漂移 | 只留最近一版加链接 |
| 手写 TOC 与标题对不上、图片裂图 | 点进去是空的 | 交付前逐条点一遍 |

## 自检：交付前逐条过

每条只有过 / 不过。

1. 首屏不滚动就能看到项目名与一句话定位。
2. 项目有界面或可见输出时，首屏给了演示图（纯库可跳过）。
3. 定位句 ≤120 字符，说清"是什么 + 给谁"。
4. 定位句里没有营销形容词（"强大""革命性""一站式"）。
5. 安装块逐字复制可跑通，没有 `<...>`、`YOUR_`、`...` 残留。
6. 安装节给了跑通后的预期输出。
7. 每个 `##` 章节都能对上读者分层表中的一行。
8. 全文没有逐文件说明。
9. 全文没有开发过程与手写测试数字。
10. 徽章 ≤5 枚，且每枚回答一个真问题。
11. 每个徽章与每张图都有 `alt`。
12. 图片与链接用仓库内相对路径，不用本机绝对路径。
13. 每个代码块都标了语言。
14. `#` 只有一个，标题不跳级。
15. 手写 TOC 与 `##` 标题逐条一致（没有 TOC 则跳过）。
16. 许可在最后并写明 SPDX 标识。
17. 外链、相对链接、图片全部点过，没有断链与裂图。
18. 全文没有只对改代码的人有意义的段落：`ctx` 原语、`src/` 模块职责、内部路由、字段清单。
19. 每一节都能说出它在决策链上回答哪个问题；库 / CLI 通常落在 ≤150 行、`##` ≤8，超了先问是不是塞了该链接走的内容。
20. 至少一条命令块能原样复制跑通，且贴了真实输出。
21. 视频没有提交进代码分支；用的是托管附件 URL 或外链。
22. 徽章多于一枚时，全文 `style` 参数与色系统一。

第 5、6、15、17、19、20、21、22 条的取证动作见 `references/self-check.md`；徽章、深浅色图、折叠区的可复制片段见 `references/visual-cookbook.md`。
