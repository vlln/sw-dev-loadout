## 原文为什么有效

| 位置 | strip-bom 的实际做法 | 可迁移结论 |
|---|---|---|
| 标题后 | 一句动词短语说明输入对象和处理动作 | 不先讲技术栈，不用“强大、灵活”代替用途 |
| 背景 | 仅补 BOM 与 UTF-8 的必要背景 | 只解释会影响正确使用的概念 |
| Install | 一个主要安装命令 | 主路径不与所有生态安装方式竞争 |
| Usage | 导入函数、给具体字符串、紧随返回结果 | 输入、调用、结果形成最小闭环 |
| Related | 指向 CLI、Buffer、Stream 变体 | 相关任务用链接分流，不把其他产品文档复制进来 |

源文还有居中的商业支持尾注，因此“极简”不是禁止所有 HTML；本 skill 为终端可读性默认不用装饰性 HTML。源文安装块含 `$`、未标语言、未写独立 License 节；本 skill 的可复制命令、语言标签和许可收尾是额外验收约定，不冒称源文如此。

## 成品顺序

一句话定位 → 安装 → 快速上手 → 关键配置 / 参数（有则写）→ License。

不要为凑齐结构添加特性墙、TOC、截图、架构、路线图。复杂背景、完整参数与平台列表用真实文档入口分流。

### 标题与一句话

写法：`# 项目名`，接一句“对什么输入做什么、给谁使用”。

strip-bom 的句子可以直接看出动作与输入类型；迁移时从目标项目找同样具体的主任务。CLI 应指出处理对象，而不是只说“提高开发效率”。目标读者不明确时补半句适用场景，不展开作者动机。

需要边界时紧接一句：支持什么、不支持什么、是否改写输入。边界必须来自实现 / 测试，不能为了显得专业而编造。

### 安装

内容必须回答：需要什么前提？复制哪条命令？如何确认命令已可用？

写入目标项目实际安装入口；shell 命令不带 `$`，标 `sh` 或适当语言。只保留主要平台路径，其他方式用一条文档链接。运行时版本从清单或兼容性测试核对，不从参考项目继承。

如果只是仓库脚本，写出取得脚本后的运行方法，不为了套模板虚构包管理器发布。

### 快速上手：库

借 strip-bom 的三个角色，而不是照搬包名与 API：

1. 完整导入 / 初始化，让示例能独立理解。
2. 一个真实且短小的输入，体现最常见的任务。
3. 就地说明返回值或产物，让读者知道是否成功。

返回值适合内联注释时就地给出，不强制再开一大块。异常、异步或资源清理影响最小路径时才加入，完整 API 留在链接后。

### 快速上手：CLI

借 Worktrunk 的真实顺序：“Create a worktree for a new feature”之后是命令及成功反馈，再解释列表里的状态符号。

迁移为目标工具时：

- 用任务句开头，如“检查一个输入文件”，不以参数名当章节标题。
- 小输入可以现场创建；已有样例文件则给仓库相对路径。
- 命令与输出分开；贴真实可核对的输出，未运行只能写“预期”。
- 输出里有状态符号、生成路径或退出码时，紧接解释它对下一步意味着什么。
- 主路径默认不涉及删除、覆盖或付费；不可避免时在命令前说明风险。

这些是用例组织规则，不是要求每个小工具添加交互 UI 或 GIF。

### 配置 / 参数

只列最影响主路径的选项，每个选项回答作用、默认行为和一个必要约束。没有配置就删本节。

CLI 需要时补“成功、无结果、输入失败”的退出行为；库需要时补输入类型、空值和异常边界。是否区分这些行为必须核对目标项目，不把这张清单当功能需求。

超过几项就给 `--help` 或真实参数文档入口，不在首页重新实现参考手册。

### 许可与相关入口

按目标许可证写 SPDX 与链接，不继承任何样本的许可证。相关包或变体最多留下读者会用的几个；没有就不写 Related。

## 裁剪与验收

- 原始 Markdown 能直接读懂主路径；删除图片后仍知道如何开始。
- 每个说明都与具体任务有关，不用空泛特性清单填篇幅。
- 最小示例有输入与成功信号；未知参数、输出和平台支持不猜。
- 只迁移结构；包名、命令、版本、资源路径与许可来自目标项目。
- 不复制 dbader 的 `edit autoexec.bat`、Travis 地址或手写 Release History；它们是源样本内容，不是跨项目通用要求。
