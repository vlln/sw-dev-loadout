# 状态保证与补偿

读它的时候：要给一个操作声明保证级别、要实现补偿或对账、要设计后台工作的失败语义，或要评审一处 catch 是否留下了可接受的状态。

## 四种保证级别怎么实现

### 无效果

要求：失败之前没有任何外部可观察的效果，或者失败之前的效果已经完整撤销。

实现手段：先把输入完整校验再执行（校验与执行是两个阶段，不要在写入路径中途校验）；在单次提交边界内完成；需要多次写入时先写临时位置，全部成功后再原子切换。

不能声称无效果的情况：写入了外部系统、发出了消息、产生了不可回滚的副作用。这时只能声称部分效果或已提交。

### 部分效果

要求：已生效的部分可枚举、可识别，调用者知道哪些做了、哪些没做。

实现手段：为每个可观察单元记录进度（位置、序号、id 清单）；把进度与效果写在同一个可恢复的位置；让重入能从未完成的单元继续。

调用者需要知道的部分要出现在错误类型里，而不是只出现在日志里。

### 已提交

要求：失败发生在提交之后。效果保留，唯一的回退是补偿。

实现手段：把「提交」与「提交之后的失败」分开报告——用一个显式的阶段字段或两个不同的错误类型，让调用者知道该重试还是该补偿。

补偿不是回滚：它是一次新的正向操作，可能失败，需要自己的预算与报告。

### 未知

要求：调用者按最坏情况处理。

什么情况下必须用未知：超时、连接中断在响应返回之前、对端崩溃、无法确认写入是否落地。

实现手段：给一个探测入口（按 id 查询实际状态）与一个对账入口（按时间窗比对两侧状态）。没有探测手段时，未知状态必须持续可见，而不是一次性警告。

## 补偿的设计

- 补偿操作必须自己幂等，因为它可能在「不知道原操作是否生效」时被调用。
- 补偿的失败要升级，不要静默重试；被补偿的对象可能已经被别人改过。
- 补偿的边界写清楚：补偿哪些效果、不补偿哪些（例如已经发出去的通知）。
- 补偿不是「回滚代码」：代码回滚不会撤销已经写入的数据。

## 后台工作的失败语义

后台任务、队列消费者、定时任务、长驻监督者：

| 问题 | 要求 |
|---|---|
| 谁拥有失败 | 明确到一个组件，不是「系统会处理」 |
| 重试边界 | 每条消息或每个任务的重试预算独立，不共享全局计数 |
| 毒消息 | 有终态：进死信、标记失败、或降级处理；不能无限重投 |
| 关闭时 | 停止接收新工作、完成或显式放弃在途工作、报告放弃的部分 |
| 失败可观察 | 持续失败要有持续可见的信号，不能只在启动日志里出现一次 |

「没人等结果」不等于可以降低义务：失败的后果仍然会到达某个用户或下游。

## 取消的语义

取消是一种失败，遵守同样的规则：

- 取消后状态是什么，要能说清（通常是部分效果或未知）。
- 取消不是立即生效：取消信号与资源释放之间要等完成信号。
- 取消期间的清理失败不能吞掉；它决定了「能否安全重试」。
- 已经被取消的工作不得继续产生外部效果。

## 评审一处 catch 时问什么

1. 这段捕获之后，哪些不变量仍然成立？依据是什么？
2. 后续工作依赖的前置条件，在恢复之后是否仍然成立？
3. 失败的效果是都没有、部分、已提交还是未知？调用者知道吗？
4. 重试是安全的吗？谁拥有重试？预算是多少？
5. 用户能看到什么？他知道下一步做什么吗？

五问答不完整时，这处捕获要么删掉（让它继续传播），要么补上缺的那部分。
