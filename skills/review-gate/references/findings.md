# 发现的核验与账本

读它的时候：手上有一批待核验的发现，或要判断某条该不该进作者队列、该不该重开。

## 账本的最小字段

一条发现至少含：

| 字段 | 内容 |
|---|---|
| 稳定 ID | 全程不变；跨轮次与跨评审者引用同一 ID |
| 根因类别 | 同一根因的多个表现共用一类 |
| 候选 | 首次提出的候选、当前候选 |
| 依据 | 对应的要求、风险或不变量 |
| 位置与实例 | 精确位置 + 已确认的实例清单 |
| 前提 | 故障前提，以及证明它可达的证据 |
| 同类范围 | 本次改动涉及的同类核查边界 |
| 三轴 | 真实性、重要性、归因 |
| 处置 | 修复、有意、误报、重复、范围外、被替代、例外、延期；含关闭依据 |

## 核验要回答的四个问题

1. **事实与位置准确吗？** 引用的是真实存在的代码或文本吗？故障前提可达吗？用测试、静态因果或可信的风险推理验证，不凭名字猜测。
2. **该行为是有意的吗？** 它是不是已被当前要求接受的设计？建议的修复会不会破坏正确行为？
3. **归因是哪一档？** 本次引入或加剧、相关既有、无关既有。严重后果与整改范围分开判断。
4. **足以改变决定吗？** 它会不会改变本轮的实现、接收结论或风险等级？

四问答不全时，结论是「待验证」，不是「确认」。

## 默认丢弃什么

- 纯命名与风格偏好。
- 没有行为收益的清理。
- 工具已经精确处理过的重复诊断。
- 没有因果路径的猜测。
- 未被采纳的远景架构。

真实硬约束与实际消费者影响单独判断——文档与配置也可能高风险，不能因为「只是文字」就判低。

被丢弃的 nit 不自动转成待办，也不让作者「顺手全改」。

## 合并与重开

- 同一问题换说法、或被不同人分别提出：合并到原 ID，保留两条来源。
- 已关闭的问题只有新证据或前提失效才重开；换一个评审者不构成重开理由。
- 复述同一发现的评论不产生新的行动项。

## 处置的八种结论

修复、有意行为、误报、重复、范围外、被替代、显式例外、延期。每一种都留一行依据。

「延期」要写明解除条件与谁会回头处理；「例外」要写明谁批准的、覆盖什么、不覆盖什么。八种结论混成一句「都处理了」等于没有处置。

## 类别级发现

发现一个缺陷类别（例如「所有取消路径都没等拆卸」）时：

1. 列出已确认的实例，不写「可能还有」当作结论。
2. 限定本次改动涉及的同类核查范围。
3. 按根因给一个修复单元，而不是给一串逐点补丁。

类别级发现不能变成全仓重构的许可证，也不能因为「只影响一处」就被降级成 nit。

## 轮次的记法

一轮 = 完整审查 → 处置 → 核验。不是一次 Agent 调用，也不是一条评论。

- 首轮：覆盖当前变更的完整相关影响。
- 后续轮：只覆盖原发现是否关闭，以及「上次候选 → 当前候选」的增量。
- 第三轮仍未闭环：转策略（根因级修复、拆范围、重新设计、升级），而不是继续常规互审。

轮次计数只在同一候选链上有效。换了方案或拆了范围，另起一条链并说明。
