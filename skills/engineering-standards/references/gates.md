# 门禁即代码

读它的时候：要新增或修改一个门禁、要判断某道门禁算不算合格、要写它的自证测试、或门禁红了要判断是对象错还是门禁错。

## 七条契约

一个合格的门禁满足全部七条：

1. **只拒绝一条不变量。** 做两件事的门禁在一件失败时给出误导性定位，也无法被单独豁免或单独自证。
2. **非零退出。** 失败退非零，成功退 0。不靠输出关键词判断成败，不在失败时仍退 0 打印警告——警告等于没有门禁。
3. **错误信息可执行。** 输出包含：违规的文件与位置、违规的具体内容、期望形态。人和 agent 读完就知道改哪里，不需要读门禁源码。
4. **无副作用**（除显式的 `--fix` 或 `--write`）。默认只读；CI 里跑的必须是只读模式。
5. **确定性。** 同样输入同样结果，不依赖时间、网络、机器上的可选工具、文件系统遍历顺序。需要可选外部工具时，缺失就明确跳过并说明。
6. **声明它消费源码还是构建产物。** 消费产物的门禁不能在干净检出上直接跑，必须先构建。两个平面不混。
7. **自证。**

另外两条工程要求：路径处理跨平台，分隔符归一化在入口处做一次；平台适配留在拥有它的那个门禁里，不为它建一层共享「平台层」。

## 自证怎么写

每个非平凡门禁配一个测试，做三件事：

1. 构造合成的非法输入（临时目录里的最小 fixture、内存字符串、假的包结构）。
2. 对它跑门禁逻辑。
3. 断言失败，并断言错误信息包含定位与原因。

同时至少构造一个合法输入断言通过，防止门禁变成永远失败。

纪律：

- 每一条新增或修改的接受规则，都要有对应的非法样例。加了规则却没加拒绝样例，等于这条规则没有生效证据。
- 自证测试断言的是门禁逻辑，不是真仓库状态。不要写「跑一遍真仓库应该通过」的测试——它会在任何无关改动上失败，且证明不了拒绝能力。
- 解析、图分析、组合规则这类复杂门禁优先用基于属性的测试：生成一族输入，断言不变量。
- 自证测试跟着门禁源码走，与其他测试同层归属。

## 编排

门禁一多就必须有编排器，否则没人知道有哪些门禁、该跑哪些。

- **一份权威清单**：一份源码（脚本或配置）列出全部门禁及分组，它是门禁清单的唯一归属。文档里不手抄列表，链接到这份源码。
- **分组按用途**：本地精选组（改了文档跑哪些、改了包结构跑哪些）、CI 全量组、需要构建产物的组、需要凭证的组。
- **可单独跑**：任何门禁都能单独一条命令跑起来。编排器不能是唯一入口，否则调试一个失败要跑全套。
- **失败聚合**：一次跑多个门禁时收集全部失败再统一报告，不是首个失败即中止。
- 调用包管理器或子进程时不经过 shell，避免引号与转义问题。

## 生成物防漂移

任何生成的产物都要有生成器加 `--check` 双模式：

- 生成模式：写入文件。
- 检查模式：在内存里生成 → 读已提交文件 → 逐字节比较 → 不一致即非零退出，并提示运行哪条命令重新生成。

三条硬要求：生成器确定性与幂等（排序稳定、无时间戳、无绝对路径、无随机 id）；手改生成物一律禁止，文件头写明生成命令；`--check` 进 CI 门禁组，并属于文档类改动的本地精选组。

做不到确定性的生成物无法被门禁守护，等于不受控——先把生成器修成确定的。

## 优先建哪些门禁

按性价比排序，一次只加一个：

| 优先 | 不变量 | 为什么值 |
|---|---|---|
| 1 | 文档里的相对链接与引用全部可达 | 极便宜、语言中立、立刻抓到真问题，还顺带验证整条门禁通路 |
| 2 | 生成物新鲜度（`--check`） | 把最常见的「忘了重新生成」直接消灭 |
| 3 | 决策记录格式与分类合法 | 决策记录一旦允许自由格式，半年内会退化成随笔 |
| 4 | 包与模块清单一致性（依赖声明、导出映射、入口存在） | 破损的清单在发布时才暴露，代价最高 |
| 5 | 源码注释里引用的文档路径可达 | 代码里的失效链接没人会发现 |
| 6 | 文档里粘贴的类型与源码一致 | 粘贴的示例一旦漂移，比没有示例更有害 |
| 7 | 公开导出必须有文档注释 | 契约缺失在评审里很难被系统性发现 |
| 8 | 构建产物可被外部消费者解析与运行 | 只有跑真产物才能暴露被开发期工具链掩盖的问题 |
| 9 | 字数预算 | 装了才会被遵守，但成本最高，放最后 |

在对应条件下值得装的：单仓多包的依赖图与分层约束、供应商代码改动与其清单同步、双语文档配对、死代码与重复代码检测。

## 不该做的

- **用 lint 全局关闭绕过一条规则。** 需要例外时用最窄的、带理由的局部豁免。
- **为了让 CI 变绿而放宽门禁。** 抬阈值、加豁免、跳过检查都必须是独立且有理由的决定并被记录。安全相关配置与发布策略配置永远不为此修改——升级给人类。
- **空壳门禁。** 项目里不存在该类对象时不要装对应门禁；它永远不会失败，只会训练所有人忽略输出。
- **让门禁承担判断题。** 机械可查的进门禁；需要语义判断的写进评审标准，并要求判断者产出结论、依据与证据路径。把判断题硬塞给门禁，结果是门禁被绕过或被削弱。

## 门禁自己错了

门禁是代码，也有 bug：错误不变量、过度约束、规则过时。红灯时先判别：被拒对象违规（门禁对了，修对象），还是门禁自身错了。判别不清时优先怀疑门禁——「为了变绿而放宽」会被审计，而「该放宽却以门禁为名挡住合法改动」同样腐蚀信任。

门禁自身错了：改门禁是合法且优先于豁免或跳过的动作。伴随动作：同一改动内一条决策记录 + 自证测试同步（新增或修改的接受规则配非法样例，原有合法样例保真，收紧也记录理由）。

与「放宽掩盖违规」的区分：**纠错改的是不变量本身**（行为语义变化有据可查）；**放宽是不改不变量、绕过它**（行为语义不变的例外）。定向例外必须带理由、最窄化，并自证「例外不扩散」。
