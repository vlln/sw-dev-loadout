# 决策记录

读它的时候：要写一条记录、要归档或删除旧记录、要判断两条记录是否重复，或要决定一条已实施的记录还该不该保持活跃。

## 是什么，不是什么

决策记录是改动者写的 RFC：动机、决定、被击败的备选、后果、验证契约——代码与普通文档承载不了的那部分。

它不是任务清单、迁移计划的长期归属、变更日志或状态看板。它也不是圣经：记录当时的判断，不是不可推翻的真理。

## 路径即生命周期

`{生命周期}/{分类}/yyyy-mm-dd-主题.md`，两个维度都写在路径里。

| 生命周期 | 含义 |
|---|---|
| `proposed/` | 实施前被评审的提案；尚未建成或只建了一部分 |
| `implemented/` | 决策已落地；记录决定了什么、否决了什么，并与落地形态保持同步 |
| `rejected/` | 提案被否决；仅在其理由仍能阻止一个有诱惑力的错误时保留 |
| `archived/` | 已实施且理由不再可能指导未来工作；永久冻结 |

分类取自封闭集合，由门禁校验；加分类要同时改集合与契约文档。一套通用分类：新增的用户可见能力、缺陷修复、删除表面的简化、关于发布源码的结构性决策、关于周边工具与流程的决策、测试基建与策略。

文件名里的日期是该主题**首次被提出**的日期，不是实施日期。记录之间用相对路径互链；不建集中索引文件——活跃的生命周期树本身就是清单。

## 骨架

三行头部固定：

```markdown
# Decision: <标题>

Status: <状态>
```

`Status:` 与所在目录必须一致，由门禁交叉校验：`proposed`、`implemented`、`rejected — <一行原因>`。状态行不带日期、不带括注。

正文一律以 `## Problem` 开头，且 Problem 要写成脱离解决方案也能读懂。之后按生命周期分：

- 提案期：`## Proposal` 可以用将来时；计划、迁移步骤、待决问题在未建成时属于这里。再接 `## Alternatives considered`、`## Acceptance criteria`、`## Risks`。
- 已实施：`## Decision` 用现在时描述已落地的现实；`## Alternatives considered`；`## Consequences` 记录这个取舍付出了什么、也换到了什么。

**提案期的标题出现在已实施记录里就是规划语气，门禁应当拒绝**：`Proposal`、`Plan`、`Migration plan`、`Acceptance criteria` 不得出现在 `implemented/` 里。`Testing`、`Deferred`、`Related` 只要写的是现在时事实就没问题。

被机械校验的结构标记（标题行、`Status:`、章节名、分类目录名）保持英文，正文语言随项目。

## 备选方案：强制

每条记录都必须有 `## Alternatives considered`：每个真实存在过的备选及它为何落败。一个有争议的备选可以用子节展开。

记录一个决策却不记它击败了什么，等于邀请日后重新扯皮——而这正是决策记录存在要防止的失败模式。

备选只能记录，不能编造。历史遗留记录若无法重建备选，用一个固定的机器可识别标记声明，并让门禁只对标记之前的旧文件接受。

## 取代检查

每条新记录都触发一次取代检查：搜索活跃树里覆盖同一决策或机制的旧记录，分类为：

- **完全取代**：旧记录的每一条独有理由、备选、后果、验证契约都已被新记录承载 → 在同一个改动里归档旧件。
- **部分取代**：旧记录仍有独有内容 → 保持活跃并互链，把仍有效的事实更新到位。

删除一个方向、一种默认值、一个实现、一种呈现，都属于部分取代；任何残留的持久化数据或兼容处理同样属于部分取代。

## 归档与删除

归档判据：已实施、决策完整、且其理由不太可能指导未来工作。只要它的备选、所有权边界、否定性保证、持久化与协议语义、安全规则、或「什么条件下应当重新引入」仍然有用，就保持活跃。

- 不归档提案：过时的提案要么否决，要么更新。
- 被否决的记录只在它还能阻止一个似乎有道理的错时保留，否则连同其全部关联文件一起删除。
- 判据是语义，不是字数、年龄或配额。

归档动作：把该记录的全部关联文件一起移入归档树，保留原状态并插入一行归档日期，修复或删除指向它的入站链接。这是归档过程中唯一允许的内容改动。

封存即永久冻结：此后不得编辑、翻译、重排、更新、移动、删除，也不得当作当前行为的依据。用只追加的内容哈希清单守护冻结状态。

## 合并删除

一条被**完全**取代的已实施记录，可以合并进当前拥有该决策的记录后删除。删除前，接收方必须保住：每一条独有理由、备选、后果、验证契约，以及已命名的覆盖缺口；修好全部入站链接；同一个改动内删除其全部关联文件。

部分取代不符合条件：两条都保持活跃并互链。

合并不得把旧文件改写成它的反面，也不得依赖版本历史作为理由的唯一副本。一条「新增能力」的记录，只有在该能力已从生产代码、配置、协议格式、迁移与兼容行为中完全消失，且没有任何现行文档把它呈现为可用、没有任何测试把它当作受支持行为时，才可合并进后来的「移除」记录。移除方要保住原始动机、为何不再值得、除完全移除外的备选、放弃了什么能力、重新引入的条件与完全消失的验证证据。
