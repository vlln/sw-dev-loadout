# 装进已有项目

读它的时候：要把这套标准装进一个已有项目、要判断该项目该装到哪一档，或要审计现有工程规范。

## 判档

档位不是主观选择，按客观信号判，取多数信号命中的最低档。

| 信号 | 最低档 | 中间档 | 最高档 |
|---|---|---|---|
| 预期寿命 | 一个月以上 | 持续维护 | 长期维护 |
| 持续集成 | 可以没有 | 有 | 有，且分组多 job |
| 协作者（含 agent） | 1 | 2 以上 | 多且并行改动 |
| 外部消费者 | 无 | 有或计划有 | 有 |
| 契约面数量（公开接口、持久化格式、协议、配置、对外可见输出） | 0–1 | 2–4 | 5 以上 |
| 生成物 | 无 | 有 | 多个 |

低档不是简陋版，它是与项目规模匹配的正确形态。**升档是一个独立的、被记录的决定**，不是随手加脚本。

同时判定并写下阶段取舍档案：当前站在「基础正确性」还是「兼容性负担」一边，以及这个站位何时失效。

## 先扫描，再谈动作

扫描阶段不改任何文件。扫描对象：

- 根目录与子目录的常驻指令文件、贡献者指南、README。
- 已有的决策文档（ADR、RFC、设计文档目录）。
- 已有的检查：CI 配置、hook 配置、lint 配置、校验脚本、包脚本里的检查入口。
- 已有的测试：目录结构、框架、覆盖率配置、快照与固定数据目录。
- 生成物：搜索生成标记与「请勿手工编辑」声明。
- 技术栈与包结构：决定门禁用哪种语言写、装在哪里。

产出分层计划表，每项标一个动作：

| 动作 | 含义 |
|---|---|
| 新建 | 项目没有对应物，从模板实例化 |
| 合并 | 已有文件里追加需要的小节，保留原内容 |
| 改造 | 语义对应但形态不符（例如旧的 ADR 没有备选段、没有生命周期目录），转换后移入 |
| 保留并引用 | 形态不同但有效，不动它，在常驻文件里链接 |
| 跳过 | 已满足 |

逐项拿授权，每项可同意、修改、拒绝。被拒绝的项记下来，下次不要悄悄再装一遍。

## 执行顺序

1. **常驻文件先落**：它是后续一切的导航入口；此时不设字数上限。
2. **决策记录契约随后**：把「装入本体系」这件事本身写成第一条记录——选定的档位、判定依据、被拒绝的项、升档的触发条件。这条记录是后续审计的锚点。
3. **第一个门禁从文档相对链接可达性开始**：最便宜、语言中立、能立刻抓真问题，也能验证整条门禁通路（编排、CI 接线、自证测试）是否打通。
4. **收窄 hook**：把跑全量测试的提交前检查收窄。这一步常遭抵触，理由要讲清：慢 hook 会被绕过，绕过一次就永远失效。
5. **其余项按计划执行**，每装一个门禁都带上它的自证测试。

完成的判据：常驻文件里每条规则都能链接到它的家；每个门禁都能在本地一条命令跑起来，并且故意制造一次违规会失败；第一条记录已提交。

## 合并优先，隔离兜底

尽最大努力把现有内容融进体系，而不是另起炉灶再让两套并存：旧 ADR 目录改造成生命周期目录，而不是新建平行的目录；贡献者指南追加小节，而不是让规则分裂到两个文件。

只有在现有形态确实无法承载时才隔离新建，并在两边互链。

不要为了体系完整而制造空壳：没有生成物就不装新鲜度门禁，没有外部消费者就不装产物冒烟。缺失的能力写进「何时需要」，而不是先建占位符。

## 审计现有规范

任务是审计而不是安装时，用四条法则当审计轴，每条问同一组问题：

1. 这条法则对应的机制在项目里存在吗？
2. 如果存在，它是可执行的还是只是散文？谁会拒绝违规？
3. 如果有门禁，它自证过吗？故意造一个违规，它会失败吗？
4. 有没有多个家（同一条规则出现在多处）？有没有空壳（存在但从不可能失败）？

产出格式：每条法则一行结论，附依据与证据路径（命令输出、文件路径、行号）。只有结论没有依据的审计项视为未完成。

审计不改文件；修复建议按分层计划表的格式给出，等授权。
