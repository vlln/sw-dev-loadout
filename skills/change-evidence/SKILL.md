# 最小充分证据

**每个改动只跑能够覆盖它所触及表面的最窄证据，一次。**

没有「通用本地基线」这种东西。每个行为改动需要那个会因它的回归而失败的最窄测试或专用检查；只有 diff 真的触达的表面才追加更广的检查。

两个方向都错：跑得不够（改了行为却只跑类型检查），和跑得太多（默认全套）。后者的危害同样严重——它拖慢每个改动、让人对信号麻木，并且掩盖了真正的问题：「我不知道该跑什么」。正确解法是把改动面到证据的映射写下来。

## 先定表面，再定证据

不确定跑什么时，先回答「这个改动触达了哪些表面」。这个问题比「跑哪些测试」容易回答得多，而且答案可复用。

| 触达的表面 | 证据 |
|---|---|
| 某个模块或脚本的行为 | 拥有它的那个测试文件，或按用例名精确过滤 |
| 模型、用户、协议可见的输出 | 通过真实可运行入口的对应快照或端到端场景，不是替身组合 |
| 文档、决策记录、生成目录 | 文档门禁组：链接、格式、生成物新鲜度、预算 |
| 包清单、公开导出、构建配置、入口或产物路径 | 构建，加上相关清单卫生检查，加上拥有它的产物冒烟 |
| 与真实外部服务的交互 | 有凭证时跑对应的真 e2e；无凭证时如实说明 |
| 并发、生命周期、子进程、拆卸 | 该领域的专项测试，按下面的确定性规则设计 |

表面怎么枚举、边界情况怎么判（数据迁移、配置默认值、权限、错误路径）见 [触达面到证据](references/surface-map.md)。读它的时候：改动横跨多个层、或你说不清它到底触达了什么。

## 分层，每层一个归属执行点

同一层测试在同一个提交上不在归属点之外重复跑——重复运行不产生新信息，只产生耗时。

| 层 | 回答什么 | 归属执行点 |
|---|---|---|
| 单元与模块测试 | 这个模块的契约成立吗 | 本地按改动面精选；CI 覆盖率门禁内 |
| 覆盖率 | 每一行都被执行过吗 | CI 专门 job，带插桩 |
| 快照与契约测试 | 组装起来的系统对外输出符合预期吗 | CI 快照 job；本地按改动面跑单个场景 |
| 构建产物冒烟 | 发布出去的制品真的能跑吗 | CI 产物 job，必须先构建 |
| 真凭证与真外部依赖 e2e | 面对真实外部系统还成立吗 | 独立流水线，只在受信任事件上触发 |
| 平台矩阵 | 在支持的每个平台与运行时上都成立吗 | CI 独立 job |
| 发布后冒烟 | 部署或发布出去的东西活着吗 | 发布流程，每个环境一次 |

失败修复后的重跑从失败层开始，不回溯已经通过的层。

## hook、本地、CI 的分工

Git hook 故意很窄，因为慢 hook 会被绕过，绕过一次就永远失效：

- 提交前：只处理暂存区——格式化、lint（含自动修复）、空白错误、需要同步的元数据守卫、必要的再生成。
- 推送前：只跑增量的类型检查或编译这类快速全局信号。
- hook 里不跑：测试、快照、文档门禁、构建、全量卫生检查。

本地：按改动面精选证据，跑一次。CI 独占：穷尽覆盖、平台矩阵、构建产物验证、全量快照。凭证策略上，主 CI 必须在无凭证时也全绿——需要凭证的测试自行跳过——同时必须有一个预检，防止「因为缺凭证而全部跳过」被误读为通过。

## 把运行聚焦到真的会跑的用例

用运行器自己的过滤参数按文件与用例名选择，并先读它报告的「选中用例数」，再把这个运行当作证据。参数转发语法随运行器与包管理器而变，照当前工具链的规则写，不要凭记忆。

过滤器发现不了只通过配置、动态加载、子进程、worker、构建产物或外部服务到达的行为。这些要显式列出拥有它们的测试。

不得用「没有测试就算通过」之类的开关、降低阈值、或缩小被测范围来掩盖一个未被覆盖的受影响文件。如果选定的范围只因为某个聚焦测试没覆盖它就红了，补上其他相关测试，或只在确实不受影响时才缩小源码范围。

## 覆盖率与豁免

覆盖率是独立门禁：阈值按文件而不是全仓库聚合，否则新代码的零覆盖会被旧代码稀释掉。

未覆盖的行往往是门禁正确指出的死代码，不是要现补的测试——先问「这行还需要存在吗」。

行覆盖必要但永不充分：它证明行跑过，不证明功能按发布形态工作。豁免必须有成员契约，例如「某个套件被移出插桩运行的条件是：它执行到的每个被测量文件都已被其他套件完全覆盖，因此移除它不改变任何阈值结果」。需要外部工具或环境的文件，让测试自行跳过并显式豁免，使缺该工具的机器保持绿色。

## 录制与固定数据

昂贵或不确定的边界（外部 API、网络、时钟、随机源）录一次真实数据，之后所有运行从记录确定性重放。CI 强制只读重放，永不写入期望输出；录制与刷新只在本地进行，每一处差异都要被评审。

只替身化昂贵或不确定的那一个边界，下游全部保持真实。手搓的替身只能证明桥能传字节，不能证明发布出去的东西行为正确。

断言必须从外部验证世界——重新执行命令、重新读文件、查询真实状态——而不是读被测系统自己的输出。对自述输出做关键词探测，会让一个作弊的实现轻松通过。

固定数据必须在所有支持的平台上可重放。**修数据，不要放宽归一化器**：放宽归一化是把跨平台缺陷藏起来最快的方式。

## 确定性

不确定的测试比没有测试更糟：它训练所有人忽略红灯。

- **等完成信号，不等时间。** 禁止用 sleep 或延时作为同步手段；超时只用来给等待设上界，不用来做断言成立的原因。
- **原子分配资源。** 用资源所有者自己的分配器，而不是先检查可用性再晚些占用。
- **收紧进程全局状态。** 环境变量、工作目录、假时钟、区域与时区、模块 mock、注册表、全局拦截都算独占资源：优先注入，必须改时记录原值并恢复。
- **尊重平台语义。** 同一个值经过操作系统往返不一定原样返回；优先选在所有平台都成立的观察，不能时用带原因的显式跳过。
- **拆卸到静止。** 只调用关闭或终止而不等完成信号，是不完整的拆卸。
- 不对瞬态状态做单次采样断言：断言终态或完整序列。

隔离与竞态的具体做法、超时预算、平台差异清单见 [确定性测试](references/determinism.md)。读它的时候：在写涉及端口、临时目录、时钟、子进程、并发或拆卸的测试，或在调查一次偶发失败。

## 证明它真的会失败

- 有条件时，先在修复之前观察一次普通回归失败。
- 新加静态或全仓守卫时，临时引入被拒的那一例，观察预期失败。
- 竞态用屏障证明重叠，重复执行本身不是竞态测试。
- 端口、套接字、共享路径、子进程这类宿主资源，跨进程隔离是修复的一部分时，要并发跑独立测试进程。
- 断言外部状态、事件、文件、日志、退出码与拆卸，而不是信任组件自述。
- 压力跑补充确定性回归，不替代它。
- **「新证据」必须在改动前的版本上真的跑一遍。** 计划或测试清单里写「这条在旧版本上会失败」，是预测，不是证据：实测常见的是旧版本恰好也通过（例如错误栈里本来就含那行文字），或旧版本因为跳过规则先行而根本没走到这条路径。逐条跑、逐条标注通过/失败；标注与实际不符，说明计划内部有矛盾，先修计划再写实现。

## 拒绝掩蔽式修复

以下都不是确定性本地测试的根因修复：提高超时而不指出在等什么状态、加重试、把全部文件串行、吞掉错误或未处理的拒绝、弱化断言、把不稳定行为归一化掉、在清理或断言前加 sleep。

为重试保留的例外只属于有文档的瞬时外部供应商测试，且例外停在外部边界上。

把预算恢复到所在 lane 本来就给的额度、或按实测竞争把有界重试定到观察到的量级，都不算掩蔽：它们命名了在等的工作。

## 性能改动的证据

当改动的目的或声明是「更快」「更省」「更稳」时，普通行为测试不构成证据：必须有改动之前的数字、在发布形态上的测量、两侧可比的输入，以及一个在原实现上会失败的负控。

测量卡、冷热样本、端到端与分段计时的区分、放弃优化的条件见 [性能改动的证据](references/performance.md)。读它的时候：改动涉及性能、内存、启动或响应速度，或你要为一个性能结论提供可复现的证据。

## 汇报

只报告真正跑过的命令与观察到的结果。区分本地运行与 CI 证据；pending 就说 pending；跳过、重试与豁免单独列出，不混入「通过」。CI 失败先看是不是环境或平台问题，并给出该判断的依据，再归因给改动。
