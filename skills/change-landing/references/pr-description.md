# PR 描述

读它的时候：正在创建或更新一个 PR 描述，或不确定某个栏目该写到什么程度。

## 四个栏目

### 动机

- 一句话说清问题。
- 至少引用一个同仓库的 issue 或工作项。会关闭它时用 `Fixes #N`、`Closes #N`、`Resolves #N`；只提供上下文时用 `Refs #N`。
- 别的 PR 的编号不算 issue 引用；放在 HTML 注释、代码块或行内代码里的引用也不算。

### 变更

分两类写，各自没有内容时写「无」：

- **接口变化**：命令、标志、配置键、环境变量、公开导出、插件注册值、协议、持久化格式。
- **行为变化**：用户、模型、开发者与系统能观察到的结果，包括默认值、性能、时序与输出。文档与 agent 指令的改动，对它们的读者来说也是行为变化。

只写 diff 保证、且测试覆盖到的行为。

### 测试

先测试设计，后测试条目。

**测试设计**按变更类型选形式：

| 变更类型 | 测试设计要显示什么 |
|---|---|
| 行为改变 | 场景 × 改前 × 改后 × 覆盖它的测试，说明改前哪些场景失败或不同 |
| 性能改变 | 每个阶段或场景的前后值，以及测量条件：机器、次数、取值方式 |
| 无行为改变的迁移或重构 | 如何证明行为没变：逐字节比较、未变的快照、新旧对照测试 |
| 纯文档 | 内容如何被检查：链接、配对、示例可编译 |

一个 PR 混多种类型时，每种类型各给一行。变更栏写「无」的项不需要测试设计。

**测试条目**：每个测试方法一条；可见地给出命令或步骤，以及它覆盖的行为。只列已经跑过的，附结果；标明来自本地还是 CI。证据放在该条目的可折叠块里，长输出可以只留命令、计数与结论摘要。

### 披露

写在它所属的栏目里，用加粗的短标签起头，不加新标题：

| 变更 | 要说明什么 |
|---|---|
| 改了某个已有测试所描述的行为 | 为什么该行为已过时 |
| 抬高了文档字数上限 | 每一条抬高的项、旧值与新值、为什么这些字是必要的 |
| 加了门禁豁免或跳过了检查 | 每一项的理由、覆盖范围、谁批准 |
| 改了产品用户可见的界面行为 | 一段可播放的演示，或一句「为什么没有」 |
| 用了术语表里没有的译法 | 译法来源，或作为待定译法提出 |

## 更新的时机

- 创建 PR 时写完整描述。
- PR 已存在后，只在描述与当前 PR 不符时更新受影响栏目。
- 栈里的每个 PR 有自己的描述，只覆盖它相对基线的这一层。
- 更新时只改需要的栏目：保留作者写的文字与媒体；删掉已不再成立的陈述；不追加一段变更历史。

## 更新的操作

1. 先把当前描述取下来存一份，避免覆盖作者内容。
2. 在本地文件里改写受影响的栏目。
3. 用平台的「以文件为 body」方式更新，而不是在网页里手改。
4. 读回一遍，确认四个栏目都在、内容与当前代码一致。

## 常见的坏描述

- 复述 diff：「修改了 a.ts 与 b.ts」。
- 把计划写进「测试」：「将补充测试」。
- 列出没跑过的检查。
- 用「小改动」「优化」代替具体行为。
- 把风险藏在披露之外的段落里。
- 描述与栈上其它层的变更混在一起。
