# 散文即契约

判据只有一条：**它承载的是契约还是转录。** 长度本身从不是缺陷。

契约是调用者、被调用者、实现者、生产者或消费者所依赖的义务、不变量、前置条件、后置条件或兼容承诺。

## 保留什么

- **行为**：它做什么，在什么前提下。
- **时序与模态**：同步还是异步、什么时候生效、能否重入、调用顺序要求。
- **异常与失败**：会抛什么、什么条件下失败、失败后处于什么状态。
- **后果**：调用它会改变什么，谁会观察到。
- **所有权**：谁负责创建、谁负责释放、谁是权威来源。
- **安全使用条件**：并发约束、资源上限、不可重复调用之类。
- **非显然的定位**：为什么这里必须是这样——一句话，加指向拥有理由的那处的链接。

## 删除什么

实现过程叙述（「首先我们……然后……」）、显然分支的证明、测试走查、评审历史与来回讨论、被否决的局部方案（属于决策记录）、代码复述（`// 把 count 加一`）、以及变更故事与版本印花（「以前」「不再」「曾经」「被重命名」「这一版」）。

理由只写在拥有它的那个位置：接口定义处、共享辅助函数处。不要在并列的每个实现旁边各抄一遍。

## 删之前先数命题

编辑之前列出这段里的每一个命题，逐项确认保留：

- 行为者与动作；
- 条件、时序与顺序；
- 模态（必须、可以、绝不）；
- 否定保证与例外；
- 所有权、副作用、失败模式与后果。

只有在每条事实从句都存活、且结果更清楚时，才删形容词、重复与叙述。**字数变少本身不是进步**：把义务删成背书是最常见的过度修剪。

## 区分语句效力

一句话的效力决定它能不能被当作依据。五类不能混写：

| 效力 | 它是什么 | 混淆的后果 |
|---|---|---|
| 要求 | 规范义务，有适用对象、条件与可观察结果 | 把评审者偏好写成「必须」，后来的人不敢改动 |
| 决定 | 已采纳的选择，带范围、理由与来源 | 把提议写成决定，等于偷偷生效 |
| 事实 | 已观察或已验证的内容 | 把一次环境结果泛化成永久保证 |
| 假设 | 尚待验证的前提 | 假设被当成既成事实，后续推理全歪 |
| 提议 | 尚未采纳的选项 | 候选内容混进现行正文，实现者自行猜测哪个优先 |

不要求每句加标签，用章节、状态或一句「待定」即可区分。观察到现有代码的行为，不自动等于用户要求。

## 只写当前态

普通文档描述当前存在的代码。直接命名活着的机制，不叙述它经历了什么。

变更故事的家是提交信息、PR 描述、决策记录、事故复盘。少数刻意保留历史证据的记录（格式检查点、发布对比、已冻结的决策）属于它们自己的契约，不因此把历史叙述扩散到别处。

## 按位置覆盖

同一份标准，不同位置的义务不同。这是「该写什么」的清单，不是单向缩短的许可——当代码、类型与结构没有传达下列契约时要补写。

| 位置 | 必须写到 |
|---|---|
| 公开 API 注释 | 调用者可见的返回区分、抛出与拒绝、副作用、所有权、时序、取消、持久性 |
| 内部注释 | 非局部结构的定向、不变量、竞态顺序、所有权、安全边界、出乎意料的失败行为 |
| 模块注释 | 角色、依赖、职责、非显然的架构选择（链接到拥有理由处） |
| 测试 | 只有非显然的测试设计：为什么需要这个 fixture、断言、平台适配、真实入口或间接观察 |
| README | 消费者契约：配置、语义、失败、限制、扩展点、对外可见的效果 |
| 提示词与界面文案 | 措辞即行为：文本、无障碍名称、提示、占位符与格式模板一起看 |
| 诊断信息 | 失败的主体或路径、违反的规则、非显然的修正方式 |

操作手册、决策记录、事故复盘的逐项义务见 [按位置覆盖](references/coverage.md)。读它的时候：在写这几类载体之一，或要判断某个位置缺了哪条契约。

空异常捕获必须写明它吞掉了什么、为什么不会有别的东西到达这里，且被包的语句只有一条。每个残留的类型逃逸要写明为什么不能用更窄的类型。待办按紧急度分级，让扫代码的人一眼分清发布阻塞项与「哪天再说」。

## 泄漏：读起来像思考过程

一个测试：**一个站在当前版本、无法访问任何会话记录、PR 线程或未提交草稿的读者，能否解析每一个引用并验证每一条断言？** 不能，就把仍然成立的事实改写成从现在这个版本可读的形态，删掉其余。

常见形态：已失效的设计会话引用（`(decision 7)`、`T4` 这类阶段标签）、栈与 PR 视角、变更叙述与版本印花、评审编排、对评审者的辩解、复述与控制流叙述、对冲与规划残留、撰写语言残留。

**不是泄漏的**：issue 引用、抑制理由与豁免理由、「没有 X 就会 Y」这类反事实回归钉、实测边界。这些是被要求的散文，删掉是另一个错误。

八类形态的判别与完整保留清单见 [泄漏与保留](references/leakage.md)。读它的时候：在清理一段读起来像推导过程的文字，或要判断某个引用该删还是该留。

## 强调与语气

- 只给真正改变行为的那个从句留强调。加粗、全大写、「至关重要」到处出现等于没有重点。
- 一段讲一件事。一段里塞进好几条规则加括注补充时，拆开或把细节降级到它的家。
- 判据用「必须、不得、应当」，不用「注意」「确保」「尽量不要」。
- 读者是专业程序员：简洁直白优于比喻。不要滥用少数抽象名词——一个词到处用就失去区分度。
- 跨引用用可机械校验的相对路径链接，不用裸文件名、编号或纯散文描述。链接检查通常只校验文件存在、不校验锚点，锚点要自己核。

## 机械与语义的分界

机械门禁查风格、结构与关键词，查不出「散文描述与实现语义不符」。绿门禁不等于文档可信。

能机械对照的（状态名、行序、接口、字段值）建漂移门禁；不能机械对照的行为与触发描述，写明由谁在哪个环节核对，并要求产出结论、依据与证据路径。

## 动手顺序

1. 确认范围与当前基线。没给范围就问清楚，不要自己扩大成全仓审计。
2. 先读拥有这段文字的代码或文档，再判断它该写什么。
3. 把待改段逐条分类：保持、补充、修剪、恢复、重构、延后。
4. 先改拥有者，再改派生物（生成的目录、快照、译文）。
5. 改完重读完整 diff：先看正确性，再看是否更短。
