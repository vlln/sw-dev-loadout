# 按位置覆盖

读它的时候：正在写操作手册、决策记录、事故复盘、README 或提示词，或要判断某个位置缺了哪条契约。

## 总原则

这是「该写什么」的清单，不是缩短许可。当代码、类型与结构没有传达下列内容时，要补写；当它们已经在本地说清时，不要重复。

## 操作手册 / 菜谱

写：前置条件、必需动作、真实入口、可观察的验证方式、简洁的告警。
不写：设计理由（链接到决策记录）、替代方案、历史沿革。

读者按步骤做完应当能判断自己成功了。缺「怎么验证」的手册会让读者在失败时无法自助。

## 决策记录

写：Problem（脱离解决方案也能读懂）、决定、被击败的备选与原因、后果（付出了什么、换到了什么）、验证契约、已命名的覆盖缺口。
不写：迁移计划的长期维护、验收清单、任务分派、状态看板。

已实施的记录用现在时描述现实；提案期标题（Proposal、Plan、Acceptance criteria）不得留在已实施的记录里。

## 事故复盘

写：事故序列、证据、因果链、影响、预防措施。
不写：重复的说服性叙述、与因果无关的实现细节。

复盘的读者是未来的维护者，他要判断的是「这条预防措施是否覆盖了那条因果链」，不是「当时谁做了什么」。

## README

写：消费者契约——配置、语义、失败模式、已知限制、扩展点、对外可见的效果。引用由本包拥有的稳定对外文本；生成目录与跨包归属用链接。
不写：复述 API 注释、别的模块的事、安装说明以外的维护者笔记（安装说明属于发布侧）。

## 提示词与界面文案

措辞即行为：改一句提示词可能是行为变更，需要自己的证据。

- 文本、无障碍名称、提示、占位符、格式模板一起看，不要只改看得见的那一句。
- 本地化由接收方的机制拥有：文案进类型化的字典，通过显式的本地化属性到达无框架依赖的原始组件。
- 保留用户、模型与协议数据，以及代码标识符原样。
- 英文界面文案用句首大写：只有第一个词、专有名词与产品名大写。中文文案遵其中文习惯。
- 模型可见文本的改动，更新拥有它的可运行快照；界面可见文本的改动，附上拥有它的证据。

## 诊断信息

写：失败的主体或路径、违反的规则、非显然的修正方式。
不写：内部执行叙述、堆栈之外的过程日志。

读者看到这条信息时，应当知道「哪里错了、违反了哪条规则、下一步做什么」。

## 测试注释

只写非显然的测试设计：

- 为什么这个固定数据必须存在（它保护的是哪个前提）。
- 为什么这个断言盯的是外部状态而不是组件自述。
- 为什么这里需要平台适配、真实入口或间接观察。
- 为什么这个用例的顺序不能重排。

不写：走查式的逐行解释、用例清单、与实现重复的描述。

## 模块注释

写：模块的角色、它的依赖、它拥有什么职责、非显然的架构选择（链接到拥有理由处）。
不写：类型形状（属于类型目录）、单模块细节（属于该模块的 README）、行为叙述（属于接口注释）。

## 边界情况

- 同一段文字服务两个读者（例如既是 README 又是帮助文本）：以拥有该事实的位置为准，另一处链接或写最小可读版。
- 生成的概要来自源注释时：让被抽取的那句在被抽取之后仍然完整，不要写成依赖上下文的半句。
- 双语文档：任一侧的改动都同时义务化另一侧，并在同一个改动内完成；不把一侧当作另一侧的「翻译产物」而放松其准确性要求。
- 无法验证的声明：写成待验证并指名验证者，而不是删掉——删掉一条未验证的真实约束，比留下它更危险。
