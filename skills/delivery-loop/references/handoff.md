# 记录与交接

读它的时候：要写下或恢复一条工作记录、要选择状态词、或准备把在途工作交给别人（或交给下一次会话的自己）。

## 记录的最小字段

一条活跃工作至少含：

| 字段 | 内容 |
|---|---|
| 归属 | 属于哪个交付或目标 |
| 目标与完成条件 | 怎么算做完，谁判断 |
| 当前责任 | 现在谁在做；空缺时写明 |
| 依赖基线 | 建立在哪个版本、哪个上游成果之上 |
| 工作位置 | 分支、工作区或目录 |
| 边界 | 可以改什么，不可以改什么 |
| 状态 | 见下表 |
| 证据 | 最近一次可定位的验证结果 |
| 下一步 | 下一件具体的事 |

计划发生重大修订时，保存原承诺与变化原因，不用新计划覆盖旧计划。

## 状态词

执行状态与结果分开：

- 执行状态：待开始、进行中、阻塞、暂停、已结束。
- 结束结果：成功、失败、取消、被替代。

「已结束」不等于「成功」；「成功」不等于「已验收」；「已验收」不等于「已交付」。四个词各自需要自己的依据。

阻塞要写清在等什么、谁能解除；暂停要写恢复条件；取消要写成果保留与依赖处置。

## 停止时保存什么

计划性停止之前，把下列内容落到文件里：

1. 工作位置与最近版本（分支、工作区、产物路径）。
2. 未提交改动的状态：有哪些、属于谁、为什么还没提交。
3. 已完成并已验证的项。
4. 待验证的项，以及它们各自缺什么才能验证。
5. 仍在运行的后台任务及其标识、产物位置、如何取回状态。
6. 阻塞与未解问题。
7. 下一步动作，具体到可以直接执行。
8. 相关决定与授权的链接。

需要版本锚点时按项目策略创建；不为保存状态而提交与本次无关的内容，也不把敏感信息带进提交。

## 恢复（接管）的顺序

1. 读入口、当前交付与相关工作记录，确认目标、范围、基线与授权边界。
2. 只读盘点现实：目录、仓库、分支、工作区、未提交改动、仍在运行的任务与产物。不重复启动已有任务。
3. 明确旧执行者是否仍活动。接管前协调责任，确认哪些工作区、验证与共享资源可以安全操作。
4. 在可安全操作的范围内，核对最后检查点与当前状态是否一致。
5. 重跑最小必要验证，或说明哪些结论可以复用及其依据。
6. 记录差异与处置：继续、修复、重新验证、交接、暂停、废弃。保留有效成果。
7. 更新责任与下一步，然后继续。

## 接手时的三条禁令

- 不凭文件时间老旧判定「没人用了」：不动别人未提交的成果，不清理、不 stash、不 reset。
- 不在未确认安全时启动可能抢占端口、数据库、构建目录或外部额度的验证。
- 不把「旧执行者可能还在跑」当成「我也可以再跑一遍」。并发写同一工作区会互相覆盖。

## 交接时要能回答

- 还承诺什么、不承诺什么？
- 现在卡在哪、谁能解开？
- 下一步做什么，具体命令或文件是什么？
- 哪些证据仍然有效、哪些需要重跑？
- 哪些决定还有效、哪些已经过期？
