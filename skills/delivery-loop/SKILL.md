# 推进一轮交付

沿用项目已有约定；没有约定时用本文的默认。目标是让下一次接手的人——或下一次会话的自己——能从文件系统恢复出四件事：还承诺什么、谁在做什么、卡在哪、下一步是什么。

## 五条不变式

| 不变式 | 它排除的失败 |
|---|---|
| 目标与重要取舍来自用户或有权者 | 角色名、审查通过、自写的批准记录被当成授权 |
| 讨论、采纳、排期、执行是四件事 | 「讨论过」被当成「正在做」 |
| 实施完成、验证通过、验收接受、实际交付、运行健康是五个不同声明 | 代码合并被当成承诺兑现 |
| 进度与恢复点落在持久化资料里 | 状态只存在于聊天、临时 todo、不可访问的后台任务 |
| 共享基线变化传播到受影响工作、消费者与证据 | 一处契约改了，别处仍按旧契约验证 |

## 先定位这次输入

每次新输入先回答：它属于哪个承诺、当前承诺是什么、哪些决定还有效、下一步是什么。只确认「现在在哪个阶段」不够。

输入的效力分七类：提问或探索、澄清、候选改进、缺陷、范围调整、暂停或撤销、明确执行指令。分类只服务于行动，不必向用户逐条报出标签。

- 范围内且低影响：直接处理。
- 只问可行性：回答讨论，不自动排期或实现。
- 改变本轮承诺：说明影响，给一个推荐处置。

结束条件：这次输入被回答、采纳、延期、拒绝、撤回，或交给了明确的澄清工作。不存在「讨论过所以正在实现」的状态。

## 三种结论与授权复用

| 结论 | 含义 | 不能自动推出 |
|---|---|---|
| 需求或范围确认 | 已采纳某个目标或行为 | 已排期，或允许生产操作 |
| 技术可接受性 | 方案足以满足用途与约束 | 有权改变目标、承担预算、执行发布 |
| 执行授权 | 可在指定对象、范围与条件下实施动作 | 同类的所有未来对象、环境与副作用 |

一次表达可以同时形成三种结论，只能按实际内容解释。执行重要动作前按五项核对已有授权是否可复用：来源（谁说的、委托是否真实）、对象（这次的要求、工作、版本、环境是否仍被覆盖）、边界（允许做什么、明确不做什么、预算与外部影响）、条件（约定的验证、观察、恢复是否满足）、变化（是否被撤回，或已被新信息推翻）。

全部适用则复用，只对缺口与变化请求决定。「按建议走」按被指向的那条建议解释；「看起来不错」可能只是方案认可。生产切换、付费资源、数据删除若仍无可靠覆盖，暂停这些动作并澄清，其他已授权且可独立进行的工作继续。

授权覆盖与证据覆盖是两件事，新旧候选之间的授权不互换：新提交、手工解决冲突、环境或数据变化，都要做差额复审。

## 六个阶段

阶段是推进条件，不是操作手册。

**流程深度与改动规模成比例。** 小型、低风险、可逆的修正按项目许可简化；微小确定性改动可以有据裁剪评审与记录。判断依据是爆炸半径、可逆性与未知量，不是"规则里写了就每样都做"——过度流程和跳过流程一样是失误，只是它不报错。

| 阶段 | 推进条件 |
|---|---|
| 立项与接入 | 目标、成功条件、责任、入口就绪；接入已有项目时不伪造历史 |
| 设计与承诺 | 承诺可验收，共享边界足以协作，重要取舍与未知有处置 |
| 工程准备 | 对即将执行的范围，必要能力可用，关键门禁能识别错误 |
| 实现与集成 | 当前承诺已集成，受影响验证有依据，偏差已处置 |
| 验证与验收 | 对明确候选与基线做整体验收，未满足项与残余风险有结论 |
| 交付与观察 | 在授权内交给实际消费者，接收、观察、恢复与后续责任明确 |

默认按依赖推进，允许满足局部前提的工作重叠：下一版设计可以与当前版验收并行，局部返工不让无关工作倒退。不能通过改阶段标签省掉交付关口。开发期尽早连接真实关键路径，允许系统、性能、安全验证前置；正式验收仍面向实际候选。

紧急修复可以缩小范围与记录粒度，不跳过必要验证与授权，也不夹带无关功能。

工程准备只补当期缺口：对照本次工作的真实执行方式，确认构建、验证、隔离、持续检查与交付入口可用，并让关键能力对受控坏样例真的失败一次。能力清单、缺口记法与自证方式见 [工程准备](references/readiness.md)。读它的时候：一轮工作即将开始而上述能力不确定可用，或验收发现门禁、环境与替身不可信。

接入已有项目时保留原生规范、现有标识、布局与有效成果；区分已确认的要求、观察到的实现与未知意图；不编造过去的批准。部分接入可以，但要在入口标明采用范围与版本，旧状态词要说明含义，不留两套互相矛盾的生效规则。接入的结果是「接手者能继续工作」，不是「目录存在或元数据合法」。

## 变更传播

范围、关键约束、共享基线、优先级或完成条件变化时，先描述影响：哪项承诺被增加、替换、延期或取消；受影响的契约、数据、消费者与并行工作；已完成成果哪些保留、哪些验证待重验；对依赖、关键路径与交付条件的影响。

给一个推荐处置及原因：本轮吸收、用其他范围替换、下一轮、先探索、暂停、关闭旧交付。用户明确坚持时按其选择重排，不继续争取同一批准；新出现的安全、数据、费用边界仍单独处理。

六步传播流程与连续插单的净范围评估见 [变更传播细则](references/change-control.md)。读它的时候：正在改动已承诺的范围，或在处理连续插单。

## 记录

最小状态集：待开始、进行中、阻塞、暂停、已结束。已结束另记结果：成功、失败、取消、被替代。同一个 done 不能同时表示「执行结束」和「验收成功」。

更新时机：重要决定、范围变化、里程碑、阻塞与解除、认领与交接、集成、计划性停止。长任务在可恢复的检查点保存，不逐次工具调用写报告。

字段清单与状态词用法见 [记录与交接](references/handoff.md)。读它的时候：要写下或恢复一条工作记录，或准备把工作交给别人。

## 停止、交接与恢复

计划性停止时保存：工作位置与最近版本、未提交改动状态、已完成与已验证、待验证内容、重要后台任务及其标识、阻塞、下一步、相关决定链接。暂停写明恢复条件；取消说明成果保留与依赖处置，不伪称完成原目标。

接手顺序是：读入口与记录确认承诺与授权 → 只读盘点现实（不发重复任务）→ 确认旧执行者是否仍活动并协调责任 → 核对最后检查点 → 重跑最小必要验证或说明可复用依据 → 记录差异与处置 → 更新责任与下一步。

不能凭文件时间老旧判定可以接管或清理。无法确认安全时，不改动该工作区，也不启动可能抢占资源的验证。

## 证据与验收

证据至少可定位：被验证的要求或风险、对象与修订、方法与命令、关键环境与数据条件、结果与限制、原始产物位置。

需求、代码、依赖、配置、环境或数据变化时，判断哪些证据仍有效；不自动清空全部证据，也不因某一层测试跑过而禁止回归。分支上的 PASS 不能拼成从未运行过的集成候选的 PASS。覆盖率数字与验收清单不能代替业务行为断言；不得靠删断言、隐藏失败、无解释跳过来取得绿灯。

验收时明确：本次承诺、要求基线、候选对象、实际消费方式。核验消费者真正拿到的东西——安装后的包、二进制、部署服务、生成的产物——开发环境的绿灯不能替代。然后汇总有效证据、未满足项、已知缺陷、偏差与残余风险，区分测试结论、技术评审与验收接受。

实施完成不等于验收通过；接受某项风险不等于把 FAIL 改成 PASS。

## 交付

核对授权、候选身份、版本、环境与前提。交付内容必须与已接受对象相同，或已有明确的变化影响判断与补充证据。

执行有授权的交付，记录版本与产物、目标、必要操作、结果与可追溯锚点。打标签本身不证明消费者已收到。在实际消费或运行环境核验核心路径与事前约定的观察条件。

恢复策略必须考虑数据可逆性与外部副作用。有不可逆迁移时，不无条件「默认回滚代码」：事先明确兼容窗口、备份与恢复验证、停止条件和已获准的动作。

交付关闭时确认范围处置、问题归属、支持责任与历史记录；复盘聚焦改变下一轮行为的经验。项目结束或转向时也要明确保留成果、归档责任与未完成目标。

## 结束前自检

- 当前承诺与实际工作一致，偏差有处置。
- 重要决定与授权边界能被下一次接手还原。
- 受影响的基线、消费者与证据都有处置，没有未通知的契约变化。
- 下一任执行者能凭记录接手，而不是凭对话回忆。
- 每个完成声明都有真实依据，且声明的层级说得清。
